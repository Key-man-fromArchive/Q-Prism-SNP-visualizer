# Q-Prism 다중 파일 작업공간 PRD

## 1. 문서 목적

이 문서는 Q-Prism SNP Visualizer의 기존 단일 활성 세션 모델을 유지하면서, 사용자가 분석 화면을 떠나지 않고 여러 PCR 파일을 업로드하고 파일별 작업 상태를 오가도록 하는 기능을 정의한다. 이 기능에서 “업로드”는 파일 전송·형식 검증·파싱·세션 생성을 뜻하고, “분석”은 cycle 추천과 클러스터링 실행을 뜻한다.

## 2. 문제와 목표

현재 첫 화면은 여러 파일을 받을 수 있지만 다중 업로드 후 프로젝트 탭으로 이동한다. 분석 중 새 파일을 추가하려면 현재 세션을 닫고 업로드 화면으로 돌아가야 하며, 다시 이전 세션을 열 때 cycle·필터·선택·작업 표면이 복원되지 않는다.

핵심 목표는 다음과 같다.

- 분석 화면 우측 상단의 `파일` 버튼에서 우측 드로어를 열고 파일을 추가한다.
- 업로드 중에도 현재 분석 화면과 활성 세션을 유지한다.
- 업로드된 파일은 자동 분석하지 않고 `준비됨` 상태로 둔다.
- 사용자가 파일을 처음 열면 별도 확인 없이 자동 분석한다.
- 저장된 분석 결과가 있으면 재분석하지 않고 즉시 불러온다.
- 같은 브라우저 탭에서 A→B→A 전환 시 A의 cycle·필터·well 선택·분석/플레이트 표면을 복원한다.
- 이번 브라우저 작업에 연 파일과 서버에 남아 있는 최근 세션을 구분한다.
- `닫기`는 이번 작업 목록에서만 제거하고, 영구 삭제는 프로젝트 화면에서만 수행한다.

## 3. 대상 사용자와 핵심 가치

대상은 한 번의 실험 검토에서 여러 plate/run을 차례로 확인하는 실험실 분석자와 연구자다. 핵심 가치는 “파일을 다시 찾고 화면을 다시 맞추는 반복 작업 없이 분석 맥락을 이어가는 것”이다.

## 4. 범위와 우선순위

### P0: 출시 필수

1. 우측 상단 파일 버튼과 접근 가능한 우측 슬라이드 드로어
2. 드래그앤드롭·파일 선택·폴더 선택으로 다중 파일 등록
3. 파일별 대기/패키징/업로드/매핑/성공/실패 단계 상태
4. 실패 원인 보존, 파일별 재시도, 부분 성공
5. 업로드 완료 후 활성 세션을 자동 변경하지 않는 동작
6. 최초 열기 자동 분석, 기존 결과 우선 복원
7. 파일별 화면 상태 저장과 A→B→A 복원
8. 빠른 세션 전환에서 오래된 응답 폐기
9. 이번 작업과 최근 세션 구분, 작업 목록 닫기
10. CSV/TSV/TXT/RDML/RDM preview·매핑 대기열과 CFX XML 묶음 처리
11. 선택 파일 수·총 원본 크기·기존 파일별 크기 제한
12. KO/EN, 라이트/다크, 키보드와 스크린리더 지원

### P1: 안정화

- 새로고침 후 같은 탭에서 이번 작업 목록과 파일별 화면 상태 복구
- 손상되거나 유효하지 않은 브라우저 저장 상태 자동 폐기
- 업로드 실패·세션 만료·권한 상실에 대한 세분화된 안내

## 5. 상세 기능 요구사항

### FR-1 파일 드로어

- 인증된 화면의 헤더 우측에 `파일 N` 버튼을 둔다. N은 이번 작업 목록의 세션 수이며 업로드 큐 항목은 별도 진행 배지로 표시한다.
- 드로어는 데스크톱에서 우측 고정 패널, 좁은 화면에서 전체 폭에 가까운 modal drawer로 열린다.
- 드로어를 열고 닫아도 활성 분석과 현재 화면 상태는 유지한다.
- Escape는 드로어를 닫고, 닫은 뒤 포커스는 파일 버튼으로 돌아간다.

### FR-2 업로드 큐

- 사용자는 활성 분석 중 파일을 drop하거나 파일/폴더 선택기로 추가할 수 있다.
- 업로드는 한 번에 한 항목씩 입력 순서대로 실행한다.
- 각 항목에 표시명, 원본 크기, 형식, 단계 상태, 오류와 재시도 동작을 표시한다.
- 한 항목이 실패해도 나머지 항목은 계속 처리한다.
- 업로드 완료는 세션 생성까지다. 완료 직후 분석을 시작하거나 현재 파일을 전환하지 않는다.
- 같은 로컬 파일을 같은 enqueue 동작에서 중복 선택하면 하나만 등록한다. 기존 서버 세션과의 내용 중복 판정은 하지 않는다.

### FR-3 형식별 동작

- `.eds`, `.xls`, `.xlsx`, `.pcrd`, `.zip`은 각각 독립 작업 항목/세션으로 처리한다.
- 같은 drop 또는 폴더 선택에서 들어온 `.xml` 파일은 모두 하나의 CFX 묶음으로 패키징하고 하나의 작업 항목/세션으로 표시한다. 혼합 선택에서는 다른 raw 파일은 각각 별도 항목이다.
- XML 묶음의 실패·재시도 단위는 묶음 전체다.
- `.csv`, `.tsv`, `.txt`, `.rdml`, `.rdm`은 기존 `UploadZone`과 같은 preview/mapping 경로로 처리한다. 매핑 마법사는 한 번에 한 항목만 열며 완료 후 parse API를 호출해 업로드 성공 상태로 전환한다.
- 매핑 preview는 서버에서 30분 만료될 수 있다. 만료 시 원본 `File`이 메모리에 있으면 preview를 다시 만들고, 없으면 파일 재선택을 요청한다.

### FR-4 제한

- 서버의 기존 파일별 제한 50MB와 ZIP entry/비압축 크기/압축률 방어를 유지한다.
- 한 번의 추가 동작은 형식과 관계없이 원본 파일 20개, 총 원본 크기 500MB를 넘을 수 없다.
- XML 패키징 결과도 서버 파일별 제한을 통과해야 한다.
- UI 제한은 빠른 피드백을 위한 방어이며 서버의 파일별 검증을 대체하지 않는다.

### FR-5 세션 열기와 분석

- 업로드 성공 후 `이번 작업` 항목을 누르면 현재 화면 상태를 저장하고 기존 detail API로 선택한 세션을 연다. view state는 `sessionStorage`, 기존 분석 결과는 서버 저장 결과에서 불러온다.
- 기존 분석 결과가 있으면 그 결과와 저장된 view state를 복원하고 자동 분석하지 않는다.
- 결과가 없으면 view state 적용이 끝난 다음 cycle 추천과 클러스터링을 한 번 자동 실행한다.
- 분석 중에도 사용자는 다른 파일로 전환할 수 있다. 백그라운드 완료 응답은 session ID를 확인해 다른 활성 화면에 적용하지 않는다.
- 열기 실패 시 기존 활성 분석은 그대로 유지하고 drawer에 오류를 표시한다.

### FR-6 파일별 상태 복원

복원 대상은 다음과 같다.

- current cycle과 data window
- 선택 well 목록과 단일 선택, 선택 group
- 선택 항목만 보기, empty/manual/auto cluster 표시 필터
- `플레이트 설정`/`분석` workspace surface
- ROX/background 표시 모드와 scatter 도구·축 모드/수동 범위

스크롤 위치, 재생 여부, 열린 context menu/modal, hover/drag 중 상태, 업로드 dialog는 복원하지 않는다. 저장 상태가 없으면 selection을 비우고 session의 ROX/background 제약을 반영한 기본값을 사용한다. 이번 작업 목록과 view state는 현재 브라우저 탭의 `sessionStorage`에만 저장한다.

### FR-7 이번 작업과 최근 세션

- `이번 작업`은 현재 브라우저 탭에서 업로드했거나 최근 목록에서 연 세션이다.
- `최근 파일`은 기존 `GET /api/sessions`가 반환하는 현재 사용자 소유 세션 중 이번 작업에 없는 항목을 `uploaded_at` 최신순으로 표시한다.
- 최근 파일을 누르면 이번 작업에 추가한 뒤 연다.
- 작업 항목의 `닫기`는 목록에서만 제거한다. 활성 항목을 닫으면 남은 작업 목록의 첫 번째 항목을 열고, 없으면 업로드 빈 상태를 보여준다.
- 영구 삭제 동작은 드로어에 두지 않는다. 프로젝트 화면으로 이동하는 링크만 제공한다.

### FR-8 경쟁 조건과 데이터 격리

- 세션 열기마다 증가하는 generation 또는 request ID를 발급한다.
- 모든 session-dependent 응답은 요청한 session ID와 최신 generation이 모두 일치할 때만 활성 store에 적용한다.
- generation과 session ID 검증으로 오래된 응답을 폐기한다.
- 세션 전환 시 이전 세션 데이터를 빈 store로 먼저 교체하거나 대상 캐시로 원자 교체해 이전 파일의 well/plot이 새 파일명 아래 보이지 않게 한다.
- 사용자 권한 범위를 넘는 세션은 기존 목록/detail/분석 API에서 거부한다. view state는 서버 API를 사용하지 않는다.

## 6. 사용자 스토리

- 분석자로서 현재 plate를 보면서 다음 run들을 업로드하고 싶다. 그래야 업로드 때문에 분석 맥락이 끊기지 않는다.
- 분석자로서 준비된 파일을 클릭할 때 처음이면 자동으로 분석되길 원한다. 그래야 반복적인 분석 버튼 조작이 없다.
- 분석자로서 이전 파일로 돌아왔을 때 cycle과 선택 상태를 그대로 보고 싶다. 그래야 비교하던 위치를 다시 만들지 않는다.
- 분석자로서 파일 하나의 실패 이유와 재시도 버튼을 보고 싶다. 그래야 성공한 파일까지 다시 올리지 않는다.
- 분석자로서 table import는 순서대로 매핑하고 싶다. 그래야 여러 매핑 dialog가 겹치지 않는다.
- 관리자로서 영구 삭제가 기존 프로젝트 화면에만 있길 원한다. 그래야 작업 목록 닫기와 데이터 삭제를 혼동하지 않는다.

## 8. 가정, 위험, 대응

### 가정

- 파일 전송 후 서버 파싱과 session 생성은 분석이 아니며 업로드 단계에서 허용된다.
- 세션과 분석 결과는 기존 SQLite 및 in-memory restore 흐름으로 30일 보관된다.
- 한 브라우저 탭에서 이번 작업을 이어가는 것이 핵심이며, 열린 작업 목록과 view state는 `sessionStorage`에만 저장한다.
- 새 탭·다른 브라우저·다른 기기에서는 최근 업로드 세션만 서버에서 다시 찾을 수 있고 view state는 공유되지 않는다.

### 주요 위험

| 위험 | 대응 |
| --- | --- |
| 여러 컴포넌트의 늦은 fetch가 새 세션 store 오염 | 공통 open generation과 응답 적용 전 session ID guard |
| 기존 전역 settings가 세션 간 누출 | 복원 대상 필드를 명시하고 세션 전환을 단일 coordinator에서 원자 처리 |
| CSV preview TTL 만료 | 큐에 원본 File 보유, 만료 재-preview, 재선택 fallback |
| 대규모 XML 패키징이 메인 스레드 정지 | 순차 패키징, 단계 상태 표시, 20개/500MB 사전 제한 |
| 작업 목록 닫기와 삭제 혼동 | 닫기 문구와 설명, 드로어에서 delete 제거 |
| 브라우저 새로고침 후 File 객체 손실 | 완료 세션만 작업 목록 복구, 미완료 항목은 재선택 안내 |
| 브라우저 저장 state가 손상됨 | store hydration 실패를 격리하고 session별 기본값 fallback |

## 9. 비목표

- 업로드 즉시 모든 파일을 자동 분석하는 batch analysis
- 여러 세션 결과의 동시 비교 알고리즘 또는 프로젝트 요약 변경
- 드로어에서 서버 세션 영구 삭제
- 원본 업로드 파일의 장기 보관이나 업로드 재개(resumable upload)
- 여러 사용자 간 실시간 공동 작업, 다른 기기 간 작업 목록 동기화
- parser/클러스터링 알고리즘·판정 기준 변경
- CSV의 preview-only assay mode를 새 분석 모드로 확장

## 10. 벤치마킹과 검증 계획

행동 모델은 브라우저의 탭 전환, IDE의 열린 파일/최근 파일 분리, 클라우드 업로드 패널의 항목별 진행·재시도 패턴을 참고한다. 이는 제품 적합성을 입증한 외부 조사 결과가 아니라 설계 가설이다.

| 항목 | 현재 분류 | 검증 방법 |
| --- | --- | --- |
| 우측 드로어가 작은 dropdown보다 적합 | 가설 | 내부 사용자 5명에게 10파일 업로드/전환 과업, 완료 시간·오클릭 측정 |
| 업로드 후 자동 전환하지 않는 것이 안전 | 합의된 요구 | E2E와 사용자 확인 |
| A→B→A 상태 복원이 재작업을 줄임 | 합의된 요구/가설 | 복원 전후 동일 비교 과업 시간 측정 |
| 세션/분석 결과가 서버에 영속화됨 | 현재 코드 사실 | SQLite restore 및 API 테스트 |
| table import는 매핑이 필요함 | 현재 코드 사실 | import preview/parse 계약 테스트 |

## 11. 타협 및 실패 대응

| 원래 기대 | 현재 범위 | 이유 | 향후 확장 |
| --- | --- | --- | --- |
| 모든 업로드를 곧바로 분석 | 사용자가 열 때만 분석 | 자원 낭비와 원치 않는 화면 변경 방지 | 명시적 batch analysis 기능으로 별도 설계 |
| 업로드 큐를 새로고침 후 그대로 재개 | 열린 세션 ID와 view state만 같은 탭에서 복구 | 브라우저 File 객체와 일반 HTTP 업로드 한계 | 원본 보관/분할 업로드 도입 시 재검토 |
| 모든 기기에서 같은 작업 목록 | 현재 탭의 이번 작업 + 서버 최근 파일 | 단일 사용자 흐름을 작게 검증 | 사용자별 server workspace 도입 가능 |

검증에서는 작업 전환 시간, 실패 재시도 성공률, stale response 오류를 측정한다. 드로어 사용성이 낮으면 상단 tab strip을 대안으로 검토하되 업로드 비전환과 파일별 복원이라는 핵심 가치는 유지한다.
