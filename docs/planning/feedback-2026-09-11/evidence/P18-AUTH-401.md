# P18-AUTH-401 — 단일 401이 전체 로그아웃을 유발하는 문제 조사

- Contract: `qprism-ux-followup-20260907-v1` 계열 후속 (`feedback/p18-auth-401`)
- Worktree: `worktree/feedback-p18` / 브랜치 `feedback/p18-auth-401` (main `99c7ba1`에서 분기)
- 발단: `docs/planning/feedback-2026-09-11/evidence/P16-ASG-ORDER.md` — 테스트가 만든 위조
  쿠키 때문에 `/api/sessions`/`/api/projects`가 401을 받아, 방금 성공한 ASG 로그인을
  `src/lib/api.ts:160`의 전역 `if (res.status === 401) useAuthStore.getState().clearAuth()`가
  되돌린 사건. 이번 작업은 이것이 **테스트 아티팩트가 아니라 프로덕션에서도 실제로 일어나는가**를
  가리는 것.
- 결론 먼저: **코드 읽기 + 실제 백엔드(포트 8205) 대상 라이브 재현 양쪽 모두에서, 이미 유효한
  세션이 "무관한" 401 때문에 잘못 로그아웃되는 경로를 찾지 못했다.** 이 저장소의 401은 이미
  "인증되지 않음"에만 예약되어 있고, 권한/소유권 실패는 전부 403으로 분리되어 있다. 아래에
  근거와 재현 로그를 남긴다.

## 1. 백엔드가 401을 내는 모든 지점

`grep -rn "401" app/` (테스트 제외) 결과 전부:

| 파일:라인 | detail | 트리거 조건 | 발생 시점 |
| --- | --- | --- | --- |
| `app/auth.py:262` | `Not authenticated` | `get_current_user`: 요청에 `snp_auth` 쿠키 자체가 없음 | 모든 보호 엔드포인트 (dependency) |
| `app/auth.py:266` | `Invalid or expired token` | `get_current_user`: JWT 서명 검증 실패, 만료(`exp` 경과), 파싱 실패, 또는 ASG 런치 모드인데 `auth_mode` claim 불일치 | 모든 보호 엔드포인트 (dependency) |

**권한/소유권 실패는 전부 403이다 (401 아님)** — 별도 표:

| 파일:라인 | 상태 | 조건 |
| --- | --- | --- |
| `app/auth.py:require_admin` | 403 `Admin access required` / `Admin access disabled in ASG launch mode` | 인증은 됐지만 admin이 아님, 또는 ASG 모드 |
| `app/auth.py:check_session_access` | 403 `Access denied to this session` | 인증은 됐지만 세션 소유자가 아님 |
| `app/auth.py:check_project_access` | 403 `Access denied to this project` | 인증은 됐지만 프로젝트 소유자가 아님 |

이 분리는 코드 읽기로만이 아니라 실제 서버로 검증했다(§4).

## 2. 만료/권한부족 구분 가능 여부

**가능하다 — 하지만 401 안에서는 구분이 없고, 애초에 401은 전부 "미인증" 계열로만 쓰인다.**
`get_current_user`의 세 401(`Not authenticated` / `Invalid or expired token` /
`User account disabled`)은 메시지는 다르지만 프론트가 취해야 할 행동은 동일하다 — 셋 다
"현재 이 자격 증명으로는 어떤 리소스도 접근할 수 없다"는 뜻이다. 반대로 "자격 증명은
유효하지만 이 리소스에 대한 권한이 없다"는 경우는 이 코드베이스에서 **401로 표현된 적이
없다** — `require_admin`, `check_session_access`, `check_project_access` 전부 403을 쓴다.
즉 원래 걱정했던 "만료 401과 권한부족 401이 섞여서 구분이 안 된다"는 문제는 **이
코드베이스에는 없다**. 설계상 이미 분리되어 있다.

## 3. 재현 시도

### 3-1. 코드 경로 재확인 (라이브 서버, 포트 8205, `/tmp/p18.db`)

```
POST /api/auth/login (admin) → 200, snp_auth 쿠키 발급
GET /api/sessions (쿠키 없음)        → 401 {"detail":"Not authenticated"}
GET /api/sessions (garbage 쿠키)      → 401 {"detail":"Invalid or expired token"}
GET /api/sessions (유효 admin 쿠키)   → 200
GET /api/auth/me  (유효 admin 쿠키)   → 200

admin이 user1(role=user) 생성 → POST /api/auth/login (user1) → 200
GET /api/users         (user1, 비-admin) → 403 {"detail":"Admin access required"}
GET /api/admin/dashboard (user1, 비-admin) → 403
```

→ 권한 실패는 결정론적으로 403이며, 유효한 세션이 401을 맞는 경우를 만들지 못했다.

### 3-2. "무관한 401이 유효한 세션을 지우는가" — 격리 재현

`/api/auth/asg-launch-cookie`는 (§1의) 쿠키 존재 검사가 `is_asg_launch_mode()` 체크보다
먼저 실행되므로, **로컬 인증 모드에서도** `ASG_LAUNCH_COOKIE_NAME` 쿠키가 없으면 404가
아니라 401을 반환한다. 이를 이용해 "이미 유효한 세션이 있는 상태에서, 그 세션과 무관한
엔드포인트가 401을 낼 때 무슨 일이 일어나는가"를 격리해서 재현했다:

```
(user1으로 이미 로그인된 상태, snp_auth 쿠키 유효)
POST /api/auth/asg-launch-cookie (ASG 런치 쿠키 없음, snp_auth만 있음)
  → 401 {"detail":"ASG launch cookie is missing"}
GET /api/auth/me (같은 snp_auth 쿠키로 재확인)
  → 200  ← 세션은 서버 쪽에서 전혀 무효화되지 않았다
```

이건 **백엔드가 stateless하다는 것**을 보여준다 — 401을 반환한다고 해서 서버가 그 세션의
JWT를 무효화하는 것은 아니다. 로그아웃은 순전히 **프론트가 `clearAuth()`를 부르는 부수효과일
뿐**이다. 즉 만약 프론트 코드가 이미 인증된 상태에서 이 엔드포인트를 호출하는 경로가
있었다면, 서버 세션은 멀쩡한데 클라이언트만 스스로 로그아웃 화면을 보여주는 상황이
재현됐을 것이다.

**그런데 현재 프론트 코드는 이 엔드포인트를 그런 식으로 호출하지 않는다:**
`src/lib/auth-bootstrap.ts`의 `authenticate()`는 `config.auth_mode !== 'asg_launch'`이면
`asgLaunchCookie()`를 아예 호출하지 않고, `App.tsx`의 부트스트랩 `useEffect`는
`bootstrap.current ??= ...`로 마운트당 정확히 한 번만 실행되며, 이 인증 확립 시퀀스가
끝나기 전까지는 (`isLoading`이 계속 true인 동안) 세션/프로젝트를 실제로 조회하는 하위
컴포넌트가 아예 마운트되지 않는다(`if (!isAuthenticated) return <LoginPage/>` 게이트).
그래서 §3-2의 401은 **재현 가능하지만, 지금 프론트 코드로는 도달 불가능한 경로**다 — 잠재
위험이지 활성 버그가 아니다.

### 3-3. P16이 봤던 경합의 재확인

P16 증거를 재확인한 결과(§4 원문), 그 401은 Playwright가 `page.route()`로
`/api/auth/config`·`/api/auth/asg-launch`만 `set-cookie: snp_auth=synthetic-auth-cookie`로
위조 응답하고, 뒤이어 실제 백엔드로 나가는 `/api/sessions`/`/api/projects` 호출은 목킹하지
않아서 생긴 것이다. **실제 백엔드는 이 위조 쿠키를 발급한 적이 없으므로** `decode_token`이
서명 검증에 실패해 401을 내는 것이 당연하다. 프로덕션에서는 ASG 런치가 성공하면 `snp_auth`
쿠키를 **같은 백엔드가** 발급하므로(`app/auth.py:create_access_token` →
`set_auth_cookie`), 이 쿠키/토큰 불일치 자체가 발생할 수 없다. 즉 P16이 관찰한 401은
테스트의 불완전한 목킹이 만든 아티팩트이지, 프로덕션 코드 경로가 아니다 — P16 문서의
결론과 일치한다.

### 3-4. 검토했지만 재현되지 않은/배제한 후보

| 후보 | 검토 결과 |
| --- | --- |
| 폴링/백그라운드 요청 (탭 비활성 중 실패) | `grep -rn "setInterval\|refetchInterval"` — auth 관련 주기적 요청 없음. `CycleControl.tsx`의 `setInterval`은 재생 애니메이션용, API 호출 아님. 해당 없음. |
| 늦은 응답(만료 직전 발송, 갱신 이후 도착) | 이 앱에는 토큰 회전/사일런트 리프레시가 없다(단일 발급, 고정 `exp`). "늦게 도착"해서 만료를 넘겼다면 그 시점 기준으로 **진짜로 만료된 것**이므로 401+로그아웃이 맞는 동작이다. 재현할 "거짓 양성"이 없다. |
| 세션 전환/로그아웃 직후 취소 안 된 in-flight 요청 | `clearAuth()`/로그아웃은 서버 쪽 JWT를 무효화하지 않는다(stateless, §3-2로 확인). 구 요청이 살아있는 구 토큰으로 서버에 도착하면 **그 토큰이 여전히 유효하면 200**이 온다 — 401이 아니다. 유일하게 401이 나는 경우는 그 구 토큰이 독립적으로 이미 진짜 무효(만료/비활성화)일 때뿐이라, 여전히 "진짜 무효" 케이스로 수렴한다. |
| ASG 런치 부트스트랩 중 인증 확립 전 나가는 요청 | §3-2에서 확인 — 이 401은 실재하지만 **인증 확립 전**(아직 `isAuthenticated=false`)이라 `clearAuth()`가 지우는 것은 애초에 비어 있는 상태뿐이다. `App.tsx`의 `isLoading` 게이트 때문에 하위 컴포넌트가 마운트되지 않아 사용자에게 보이는 부작용도 없다. |
| DB 잠금/일시 오류로 `get_user_by_id`가 거짓으로 `None` 반환 | `app/db.py`의 `get_db()`/쿼리들에 401로 변환하는 예외 처리가 없다 — `sqlite3.OperationalError` 등은 FastAPI 기본 처리로 500이 된다. 401로 위장되지 않는다. |
| 로그인 rate-limit(`AuthLimitExceeded`) | 429를 반환(`auth_router.py:63`), `responseError`는 `=== 401`만 체크하므로 로그인 재시도가 레이트리밋에 걸려도 기존 유효 세션은 전혀 건드리지 않는다. |

## 4. 각 후보의 보안 영향과 권장안

현재 상태(모든 401 → 즉시 `clearAuth()`)에 대한 대안 3가지와 그 트레이드오프:

| 안 | 내용 | 보안 영향 | 판단 |
| --- | --- | --- | --- |
| A. 현행 유지 | 모든 401 → 즉시 로그아웃 | 없음(현재 401은 이미 "미인증" 전용) | §1·§3에서 확인했듯 이 저장소에는 "권한부족인데 401"인 경로가 없다. 오탐(false positive)을 만드는 활성 프로덕션 경로를 찾지 못했으므로, 이 부분만 놓고 보면 **당장 앱 코드를 바꿀 근거가 약하다.** |
| B. 인증 확인 전용 엔드포인트(`/api/auth/*`)의 401만 신뢰, 나머지 401은 무시 | 예를 들어 `/api/sessions`의 401은 로그아웃시키지 않음 | **위험.** `/api/sessions`도 `get_current_user`를 통과해야 401을 내므로, 그 401은 정말로 "지금 이 쿠키로는 아무것도 못 한다"는 뜻이다. 이걸 무시하면 만료되거나 무효화된 토큰을 든 채로 화면은 계속 로그인된 것처럼 보이고, 사용자가 다음 액션(업로드 등)을 시도할 때마다 개별 실패가 반복되는 나쁜 UX가 되며, 잘못하면 만료된 토큰이 화면에 "로그인됨"으로 잔존하는 시간이 늘어난다. **권장하지 않음.** |
| C. §3-2에서 드러난 순서 버그만 수정 (`asg-launch-cookie`가 `is_asg_launch_mode()` 체크를 쿠키 존재 검사보다 먼저 하도록) | 백엔드 1줄 순서 변경 | 이건 "401 정책"을 바꾸는 게 아니라 **로컬 모드에서 이 엔드포인트가 404를 내야 하는데 401을 내는 사소한 불일치**를 고치는 것. 현재 프론트 코드가 이 엔드포인트를 그렇게 호출하지 않으므로 활성 버그는 아니지만, 향후 코드가 실수로 이미 인증된 상태에서 이걸 호출하게 되면 §3-2가 보여준 것처럼 "서버 세션은 멀쩡한데 클라만 로그아웃"이 실제로 일어난다. **백엔드 수정이 필요하고 사전 승인 대상**이라 이번 조사에서는 손대지 않았다. |
| D. 프론트에서 401을 받아도 즉시 지우지 않고 `/api/auth/me`로 한 번 더 확인 후 결정 | | **이 저장소에는 필요 없다.** `get_current_user`가 이미 모든 보호 엔드포인트에서 같은 검증을 하므로, `/api/sessions`가 401이면 `/me`도 거의 항상 401이다(둘 다 같은 쿠키/같은 `get_current_user`를 거침). 추가 확인 왕복이 만료된 세션을 조금 더 오래 살려두는 대가만 지불하고 얻는 게 없다. |

**권장**: **A(현행 유지)**를 원칙으로 하되, **C(순서 버그)** 는 별도의 작고 사전 승인 가능한
백엔드 수정으로 처리할 것을 제안한다. 프론트의 "401이면 전역 로그아웃"이라는 정책 자체는
이 코드베이스의 401 시맨틱(=항상 "미인증") 아래에서는 올바르다. 문제가 있다면 그건 정책이
아니라, 미래에 이 시맨틱을 깨는 엔드포인트(권한부족을 401로 낸다거나, §3-2 같은 순서
버그)가 추가되는 것 — 그건 리뷰에서 "401은 미인증에만 쓴다"는 불변식을 지키는 방식으로
막아야 한다.

## 5. 확신하지 못하는 지점

- **ASG 원격 서비스(`asg_client.py`)의 401 전달**: `validate_launch_token`은 ASG 원격
  서비스가 400/401/403/404/410 중 무엇을 반환하든 전부 SNP 쪽 401로 뭉뚱그린다. ASG
  원격 서비스가 "토큰 형식 오류"(400 상당)와 "토큰 만료"(410 상당)를 구분해서 보내는지
  나는 확인할 수 없었다(ASG 서비스 자체는 이 저장소 밖에 있음). 이 구분이 SNP 쪽 UX에
  중요한지는 ASG 쪽 스펙을 봐야 판단 가능하다.
- **다중 탭/다중 창 시나리오**: Zustand 스토어가 탭마다 독립적임을 코드로 확인했지만,
  실제 브라우저에서 두 탭을 동시에 띄워 ASG 런치 쿠키 경합을 실측하지는 않았다(§3의 curl
  기반 재현은 단일 클라이언트 순차 호출). 이론적으로는 스토어 격리 때문에 문제가 없다고
  판단했지만, 브라우저 레벨 실측은 하지 못했다.
- **JWT_SECRET_KEY 운영 관리**: 배포 환경에서 이 값이 재시작마다 재생성되거나 레플리카마다
  다르게 설정될 경우, 모든 활성 세션이 한꺼번에 "서명 검증 실패" 401을 맞고 로그아웃된다.
  이건 **코드가 아니라 배포 설정**의 문제라 이 저장소 안에서는 확인할 수 없었다. 현재
  기본값(`"dev-secret-change-in-production"`)은 고정 문자열이라 값이 아예 미설정이면
  최소한 레플리카 간 불일치는 없지만, 프로덕션에서 실제로 무엇이 설정되어 있는지는 알 수
  없다.

### 6-1. C — 백엔드 순서 버그 수정

`app/routers/auth_router.py`의 `asg_launch_cookie`가 `is_asg_launch_mode()` 확인보다
쿠키 존재 검사를 먼저 하던 순서를 뒤집었습니다. **상태 코드는 404를 선택**했습니다 —
근거: 이 엔드포인트는 §1의 `_complete_asg_launch`가 이미 "모드가 안 맞으면 404"로 처리하고
있고(`if not is_asg_launch_mode(): raise HTTPException(status_code=404, ...)`),
`/api/auth/login`(로컬 모드가 아닐 때 로컬 로그인을 막을 때)과 `/api/auth/change-password`도
같은 "이 모드에서는 이 표면이 아예 없다"는 뜻으로 전부 404를 쓰고 있습니다. 400은 이
저장소에서 "요청 자체는 유효한 표면에 도달했지만 내용이 틀렸다"는 뜻으로 예약되어 있고
(예: 비밀번호 강도 실패, ASG 사용자 이메일 중복), 이 경우는 그게 아니라 "이 모드에서는
이 라우트가 존재하지 않는다"는 뜻이므로 기존 컨벤션과 일관되게 404를 택했습니다.

기존 테스트 grep 결과 이 401을 직접 단언하는 테스트는 없었습니다(성공 교환 테스트만
있었음, `tests/test_asg_launch_auth.py:78`). RED 먼저 진행:
1. `test_asg_launch_cookie_still_requires_cookie_in_asg_launch_mode` 추가 — ASG 모드에서
   쿠키가 없으면 여전히 401이어야 한다는 회귀 잠금(기존 동작 보존).
2. `test_asg_launch_cookie_is_disabled_not_unauthenticated_outside_asg_launch_mode` 추가 —
   로컬 모드에서는 404여야 한다는 새 요구. 수정 전 실행: 이 테스트만 실패
   (`AssertionError: 401 != 404`), 나머지 8개는 통과 — 의도한 이유로 RED임을 확인.
3. `auth_router.py`에 `is_asg_launch_mode()` 체크를 쿠키 검사보다 앞에 추가. 재실행:
   9/9 통과(GREEN). 아무 단언도 삭제·완화하지 않았습니다.

### 6-2. A — 정책을 코드에 남김 (동작 변경 없음)

`src/lib/api.ts`의 `responseError` 바로 위에, 이 저장소의 401이 왜 항상 "미인증"만
의미하는지(권한부족은 403으로 분리되어 있음, `app/auth.py`의 세 지점 참조), 그리고 이번
조사 문서를 가리키는 주석을 추가했습니다. 앱 동작은 바뀌지 않았습니다(`if (res.status
=== 401) ...` 로직 자체는 그대로).

정책을 테스트로 고정: `lib/api.contract.test.ts`에 이미 있던 401 테스트들(blob 401, 읽을
수 없는 본문의 401 — 둘 다 `clearAuth`가 불림을 확인) 옆에, **403은 `clearAuth`를 부르지
않는다**는 테스트를 새로 추가했습니다
(`P18-AUTH-401: leaves a valid session alone on 403 (permission, not auth, failure)`).
이건 이미 있던 403 테스트(`preserves legacy string errors`)와 별개로, "인증 상태가 403
이후에도 그대로 유지된다"는 것 자체를 단언에 넣은 것입니다 — 나중에 누가 401 처리를
무심코 다른 상태 코드로 확장해도 이 테스트가 잡습니다.
