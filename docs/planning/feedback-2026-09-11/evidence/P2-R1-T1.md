## Problem

`pcrd_raw._parse_protocol()` and `eds_raw._parse_protocol()` already compute
whether a step read the plate (`has_read` / `CollectionFlag`) and the
per-cycle touchdown temperature delta (`inc_temp` / `ext_temp`), but only
used them to build a label string and then discarded them. `ProtocolStep`
had no fields to carry them. The frontend was left guessing "did this step
read the plate" from the label text (`isReadingStep(label)`), which breaks
the moment a user edits the label.

## GREEN — implementation

`app/models.py` — `ProtocolStep` gains three fields, all with defaults:

```python
plate_read: bool = False
temp_increment: float | None = None
read_channels: list[str] = Field(default_factory=list)
```

`app/parsers/pcrd_raw.py` — the `ProtocolStep(...)` construction in
`_parse_protocol()` now passes:
- `plate_read=step["has_read"]` (already computed, previously dropped)
- `temp_increment=step["inc_temp"] if step["inc_temp"] != 0 else None`
  (same `!= 0` test the existing label-building code already used to decide
  whether a step is a touchdown step; `0.0` from an absent/zero
  `IncrementOption` maps to `None`, a real non-zero increment keeps its sign)

`app/parsers/eds_raw.py` — the `ProtocolStep(...)` construction now passes:
- `plate_read=tc_step.findtext("CollectionFlag", "0") == "1"` — the raw
  per-step flag, independent of which label branch happens to fire (unlike
  the label logic, which only checks `CollectionFlag` for non-first,
  non-`PRE_READ`/`POST_READ` steps)
- `temp_increment=ext_temp if (auto_delta and ext_temp != 0) else None` —
  gated on `auto_delta` (`AutoDeltaEnabled`) in addition to `!= 0`, mirroring
  the existing label code's `if auto_delta and ext_temp != 0` guard, so a
  stray non-zero `ExtTemperature` on a non-touchdown stage does not get
  reported as a temperature increment

`read_channels` is left at its default (`[]`) in both parsers — neither
format carries a per-step channel list, only a run-wide channel→dye map, and
filling it with the run-wide list would assert "this step read these
channels" for a claim the source data does not make (per FB-05 §3-1's
explicit correction).

`app/routers/data.py`:
- `DEFAULT_PROTOCOL` updated: the touchdown annealing step now carries
  `temp_increment=-0.6` to match its existing label
  (`"Annealing (Touchdown -0.6/cycle)"`), and the final "Final Read" step
  now carries `plate_read=True` to match its existing label/intent.
- `GET /api/data/{sid}/protocol` now also spreads
  `**build_role_label_metadata(unified)` into the response, alongside the
  existing `"steps"` key — the same helper already used by
  `/amplification`, `/ct`, etc. (`app/routers/data.py:100,175,215,256` in
  the pre-change file). This gives the frontend the run-wide channel→role
  map (`role_channels`, `role_channel_labels`, `channel_labels`,
  `normalization_*`) from the response contract, so the protocol tab's
  channel card does not need to read the `data-store` cache (which can be
  stale relative to the currently open session). No existing response key
  was removed or renamed.

## D-9 — unresolved (as documented, partial block)

Per `docs/planning/06-tasks.md` §4 (D-9), this task proceeds on the backend
side and defers the **ASG-receiving-side schema validation strength**
question: whether the external ASG service's `protocol_steps` schema
accepts unknown/additional fields, requires a pre-agreed schema version
bump, or would reject/strip `plate_read`/`temp_increment`/`read_channels`
as unrecognized. This repository has no visibility into that schema or its
validation mode (strict vs. permissive), so it cannot be confirmed here.
The three fields are additive with defaults on the *sending* side, and this
task's own serialization test proves the *outgoing* payload is well-formed
JSON with the new keys present — but whether ASG's *receiving* side accepts
them is out of scope and unconfirmed. Flagging for Phase-gate review before
this reaches an ASG-connected environment.

## Test file note

`tests/test_protocol_step_read_fields.py` imports the `plate`/`data_client`
fixtures from `test_export_snapshot_csv.py` under their real names (not an
alias) — pytest fixture registration is keyed by the name the fixture
function was *defined* with, not the name it is imported under, so an
alias (`plate as _plate`) silently breaks fixture resolution (confirmed:
`fixture 'plate' not found` when tried). The one test that needs `plate`
(`test_asg_payload_serializes_new_protocol_fields`) pulls it via
`request.getfixturevalue("plate")` inside the test body instead of a
same-named parameter, so `ruff` does not flag the module-level import as an
F811 redefinition of a later same-named parameter (the pattern
`test_export_snapshot_reports.py` uses is pre-existing and already fails
`ruff check` for this exact reason — out of this task's write scope to fix).
