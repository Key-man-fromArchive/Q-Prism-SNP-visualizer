## Problem

`GET /api/data/{sid}/amplification/all` (`app/routers/data.py`, previously
around lines 254–258) returned only `allele2_dye` + role label metadata +
`curves`. It had no echo of whether normalization or background subtraction
was actually applied to the curve values it returns. The frontend overlay
therefore had to assert "normalized" straight from the *request* it sent
(`useRox` / `backgroundMode` in the store) rather than from what the backend
actually did.

That is a lie on a run with no passive reference: `normalize()`
(`app/processing/normalize.py`) silently falls back to raw values no matter
what `use_rox` asks for — the decision lives in
`_normalization_context()`, and `normalization_applies()` is the function
that reports it. `/scatter` and `/plate` already call
`normalization_applies(unified, use_rox=use_rox)` and echo `background_mode`
(`app/routers/data.py:98,176` in the pre-change file, both already importing
`normalization_applies` — see `app/routers/data.py:14`). `/amplification/all`
had no such contract.

## Where the existing decision logic was found and reused

`app/processing/normalize.py:normalization_applies()` (lines 45–58 in that
file) — the exact function already used by `/scatter`
(`app/routers/data.py:98`, pre-change) and `/plate` (`app/routers/data.py:176`,
pre-change), and already imported at the top of `data.py`
(`from app.processing.normalize import normalize_for_cycle, normalize,
normalization_applies`). No new normalization-decision logic was written;
`amplification_all()` now calls the same function with the same arguments
(`unified`, `use_rox=use_rox`) that `/scatter` and `/plate` use.

For `background_mode`, `/scatter` and `/plate` both echo the raw `background`
query parameter directly (`app/routers/data.py:92,174`, pre-change) rather
than computing a separate "actually applied" value. This is honest already:
`apply_background()` (`app/processing/background.py:100-116`) either applies
the requested mode exactly or raises `BackgroundModeError` (mapped to a 400
in `app.main`, confirmed by `tests/test_background_mode_api.py`'s
`test_a_mode_the_run_cannot_be_read_with_is_a_400_not_a_500`) — there is no
silent-fallback case to distinguish, unlike normalization. `amplification_all`
follows the identical echo-the-request pattern for consistency with the two
existing endpoints, since a 200 response can only occur when the requested
mode was in fact the one applied.

## No `app/models.py` change

The task brief listed `app/models.py` as scope "if the response schema
requires it." `amplification_all()` returns a plain `dict`, not a
Pydantic `response_model` (same as `/scatter` and `/plate`), so no schema
class needed a new field. `AmplificationCurve` (used only by the
single-well `/amplification` endpoint) was left untouched — `/amplification`
was not in scope for this task.

## GREEN — implementation

`app/routers/data.py`, inside `amplification_all()`:

```python
all_normalized = normalize(unified, use_rox=use_rox, background=background)
applied = normalization_applies(unified, use_rox=use_rox)
```

and in the response dict:

```python
return {
    "allele2_dye": unified.allele2_dye,
    "background_mode": background,
    "normalization_applied": applied,
    **build_role_label_metadata(unified),
    "curves": curves,
}
```

Both new keys are additive; `curves`, `allele2_dye`, and the role-label
metadata keys spread by `build_role_label_metadata()` are unchanged in name,
position relative to each other, or value.

## Key honesty case verified

`test_no_reference_channel_and_use_rox_true_honestly_reports_not_applied`:
a run built with `has_rox=False` (no ROX reading on any well), requested
with `?use_rox=true`, returns `normalization_applied: False`. This confirms
the endpoint reports the actual outcome of `normalize()`, not the client's
request flag.

## Backward compatibility

- Existing keys `allele2_dye`, `curves`, `channel_labels`,
  `role_channel_labels`, `role_channels`, `normalization_mode`,
  `normalization_channel`, `normalization_dye` (all spread from
  `build_role_label_metadata()`) are untouched — verified directly by
  `test_existing_fields_are_preserved_for_backward_compatibility`, which
  passed both before and after this change.
- No existing key was renamed or removed; the two new keys
  (`normalization_applied`, `background_mode`) are added, matching the same
  field names `/scatter` and `/plate` already use, so a frontend consumer
  that later reads this endpoint can reuse the same field name and parsing
  logic across all three endpoints.
- A consumer that ignores the two new keys (the current
  `AmplificationOverlay.tsx`, per FB-06 §2, and `getAllAmplification()`'s
  existing TypeScript type) is unaffected — extra JSON keys are inert to
  existing `curves`/`allele2_dye` consumers.
