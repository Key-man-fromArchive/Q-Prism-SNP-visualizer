# P2-S1-T1 — Thermal-cycling profile diagram + read-channel summary card

Branch: `feedback/p2-rawdata` (worktree `worktree/feedback-p2`)
Scope: `snp-analyzer/frontend/src/components/protocol/ProtocolThermalProfile.tsx`
(new), `ProtocolThermalProfile.test.tsx` (new), `ProtocolTab.tsx`,
`ProtocolTab.test.tsx`, `use-protocol-editor.ts`, `types/api.ts`,
`locales/{en,ko}.ts`. No backend files touched.

## Problem

P2-R1-T1 landed `ProtocolStep.plate_read` / `.temp_increment` /
`.read_channels` on the backend and widened `GET /api/data/{sid}/protocol`
with run-wide channel/role metadata. The frontend still: (a) rendered
nothing but an editable table with numbers, (b) decided whether to show the
camera marker by testing the free-text `label` for substrings
(`isReadingStep`), which breaks the instant a user renames a step, and (c)
had nowhere to show which channels were read at all.

## GREEN — implementation

### `types/api.ts`
`ProtocolStep` gains `plate_read: boolean`, `temp_increment: number |
null`, `read_channels: string[]` (mirroring the backend model exactly).
`ProtocolResponse` becomes `RoleLabelMetadata & { steps: ProtocolStep[] }`
— the same intersection pattern already used by `PlateResponse` /
`AmplificationResponse` / `ScatterResponse` / `CtResponse` for the same
`build_role_label_metadata()` payload shape, so `getProtocol()`'s return
type now carries `role_channels` / `role_channel_labels` / `channel_labels`
/ `normalization_*` with no change to `lib/api.ts` itself (it already just
forwards the response through `apiFetch<ProtocolResponse>`).

### `ProtocolThermalProfile.tsx` (new)
Inline SVG, zero new dependency. Per the task brief, **not** Plotly:
this is a fixed summary picture (temperature vs. step order), not an
exploration surface — no zoom/pan/hover value, and Plotly would mean
theming it through `plotly-theme.ts` for no interactive benefit while
costing print/PDF stability (Plotly's canvas/WebGL renderers do not
reliably rasterize the same as their on-screen output; a plain `<svg>`
does, because it *is* the print output). SVG also gets `currentColor`
dark-mode support for free — the root `<svg className="text-text">` makes
`stroke="currentColor"` track the same theme variable every other
`text-text` element in this tab already uses, with no separate light/dark
branch to maintain.

Design decisions, each maps to a written requirement:
- **X axis is step index, not real time.** `Initial Denaturation` (300s)
  and `Annealing` (5s) get equal-width segments; the step's `duration_sec`
  is rendered as a text label under its segment instead. (A
  duration-proportional axis was rejected in FB-05 for hiding the
  amplification region entirely behind one giant Initial-Denaturation bar.)
- **Y axis is temperature**, linear-scaled across `min`/`max` of all step
  start/end temperatures (with a ±5°C pad when every step shares one
  temperature, to keep a visible line rather than a divide-by-zero flat
  line at height 0).
- **Touchdown (`temp_increment`) is a diagonal, not a flat segment.** A
  step's "end temperature" is computed as
  `temperature + temp_increment * (cycles - 1)` (only when
  `temp_increment != null` and `cycles > 1`); the path draws a straight
  line from the step's start temperature to that end temperature across
  its own segment width, and a `±X°C/cyc` label is drawn near the segment's
  midpoint with an explicit `+` for positive deltas (`formatIncrement`).
  The staircase's vertical connector into the *next* step starts from this
  end temperature, so a touchdown step's actual last-cycle temperature
  — not its nominal starting temperature — is what the following step
  visually steps off from.
- **Phase bands + ×N badge, reusing the exact existing color selection.**
  `groupPhaseBands()` groups contiguous steps sharing a non-empty `phase`
  string (mirroring the `isFirstInPhase` grouping already used by the
  table) and renders one tinted background rect + label per group, with
  `×{cycles}` appended when `cycles > 1`. The color lookup
  (`getPhaseColor`) is intentionally **duplicated**, not imported, from
  `ProtocolTab.tsx`: `ProtocolTab.tsx` renders `<ProtocolThermalProfile>`,
  so importing the color function back from `ProtocolTab.tsx` would create
  a component↔component import cycle. Both copies read the same exported
  color maps from `src/lib/constants.ts` (`PROTOCOL_PHASE_COLORS` /
  `PROTOCOL_AMP_COLORS` / `PROTOCOL_PHASE_FALLBACK`, the P0-T0.2
  value-locked single source), so the two copies cannot render different
  colors for the same phase string — only the 3-line selection logic is
  duplicated, not the color values. `constants.ts` is outside this task's
  write scope, so the alternative (moving `getPhaseColor` there) was not
  available without an out-of-scope edit; flagging this as a small,
  low-risk duplication rather than silently doing an out-of-scope file
  change.
- **Read markers are keyed to `step.plate_read`, full stop.** No string
  matching against `label` anywhere in this file or in `ProtocolTab.tsx`
  after this change (`isReadingStep` is deleted, not just unused).
- **`read_channels` is never rendered per-step.** Per the task's explicit
  prohibition (and FB-05 §3-1's own correction), it is always `[]` from
  every parser today; drawing per-step chips from it would assert "this
  step read these channels," a claim the source data doesn't make. The
  field exists on the type for forward-compatibility and round-trips
  through the editor untouched, but this component never reads it.
- **Accessibility**: the root `<svg>` has `role="img"` and
  `aria-labelledby` pointing at a `<title>` (the diagram's name) plus a
  `<desc>` built from `t.protocolThermalProfileSummary(steps, reads,
  minTemp, maxTemp)` — a plain-language summary ("N steps, M plate reads,
  X–Y°C. Step order, not real time.") for anyone who cannot see the shape
  of the line. Per-step decorative elements (the 📷 glyph) are
  `aria-hidden` since the diagram-level description already states the
  read count; the *table's* existing per-step 📷 marker (now also driven by
  `plate_read`) remains the accessible, per-row way to know which specific
  step reads.
- **400px / narrow-viewport handling**: the SVG's `width`/`viewBox` grow
  with step count (`MARGIN_LEFT + steps.length * STEP_WIDTH + MARGIN_RIGHT`)
  and it's wrapped in a `overflow-x: auto` div, so a long protocol scrolls
  horizontally inside its own diagram rather than compressing into
  unreadable step widths or breaking the surrounding page layout.

### `ProtocolTab.tsx`
- `isReadingStep(label)` deleted outright (not deprecated, not left
  dead). The table's own 📷 marker condition changed from
  `isReadingStep(step.label)` to `step.plate_read`.
- `handleAddStep` now sets `plate_read: false, temp_increment: null,
  read_channels: []` explicitly on a new step, instead of relying on them
  being absent (which is what made `tsc -b` fail at RED — see above).
- New `ProtocolChannelCard` renders one chip per entry in
  `channels.role_channels` (from the hook, see below), colored
  `var(--color-fam)` for `WT`, `var(--color-allele2)` for `MT1`, and a
  neutral `var(--color-text-muted)` dot for any other role (including
  `normalization`, whose label is localized via the pre-existing
  `t.normalization` key rather than inventing a new one). It renders
  `null` — no card, no empty-state text, no placeholder chips — when
  `role_channels` is absent or empty, per the explicit instruction not to
  show empty chips or guessed values.
- `max-w-[800px]` removed from the form's `className`; the panel now
  fills the available width so the diagram and a wide table both have room
  on large screens. The table's own scroll region
  (`overflow: auto; maxHeight: 500px`) and all editing behavior
  (change/add/delete/save/cancel handlers) are untouched.

### `use-protocol-editor.ts`
Added a `channels` state slot (`RoleLabelMetadata | null`), set from the
*same* `getProtocol(sessionId)` response used for `steps` (`setChannels(res)`
right next to `setSteps(res.steps)`), and returned from the hook alongside
`steps`. This was the option chosen over having `ProtocolTab.tsx` issue a
second, independent fetch: the task brief requires reading channel data
"from the response contract, not the data-store cache" — reusing the one
request the hook already makes satisfies that with no duplicate network
call and no second source of truth to keep in sync. `save()`'s
`submitted = steps.map(step => ({ ...step }))` was already a full-object
spread before this task (verified by the two characterization tests
mentioned above), so no change was needed there to keep `plate_read` /
`temp_increment` / `read_channels` intact across a save round-trip.

### `locales/{en,ko}.ts`
Added `protocolThermalProfile`, `protocolThermalProfileSummary(steps,
reads, minTemp, maxTemp)`, `protocolReadChannels`. Reused the existing
`normalization` key for the channel card's `normalization` role label
rather than adding a duplicate.
