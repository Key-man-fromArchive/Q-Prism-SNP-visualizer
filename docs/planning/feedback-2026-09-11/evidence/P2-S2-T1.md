## 1. DOM id scoping (prop-based, not `useId()`)

Chose a `idPrefix?: string` prop (default `""`) over `useId()`, per the
task's "`useId()` 또는 prop 기반" option. Reason: an existing, out-of-scope
E2E spec (`e2e/p4-s2-analysis-tab.spec.ts:38`,
`page.locator("#toggle-overlay-btn")`) locates the Analysis-tab / per-marker
instance by its exact hardcoded id. `useId()` would have generated an
opaque id (e.g. `:r3:-toggle-overlay-btn`) for **every** instance including
that one, breaking the spec with no way to fix it (it's not in this task's
write scope). `idPrefix` defaulting to `""` keeps that instance's ids
byte-for-byte unchanged; only the new Raw data mount passes
`idPrefix="rawdata-"`.

All four fixed ids (`overlay-plot`, `overlay-container`, `toggle-overlay-btn`,
`overlay-channel-select`) plus the new `overlay-color-by-select` are now
`` `${idPrefix}<name>` ``.

Verified duplicate-id-free with both instances actually mounted at once
(`plot-cleanup.test.tsx`, "scopes DOM ids so two concurrently mounted
overlays do not collide"): renders `<AmplificationOverlay />` and
`<AmplificationOverlay idPrefix="rawdata-" />` together, asserts both
`#overlay-plot` and `#rawdata-overlay-plot` exist, ids are unique, and after
toggling both open, `Plotly.react` received two **different** DOM nodes
(`renderedNodes[0] !== renderedNodes[1]`) — the ref-based capture the FB doc
said was already safe, confirmed under the id-scoping change too.

This scenario is not hypothetical: `App.tsx` keeps `AnalysisWorkspace`
(which contains the Analysis-tab `AmplificationOverlay`) mounted at all
times once a session is loaded — only a CSS `hidden` class toggles with the
active tab (`App.tsx:186-189`) — while `ProtocolTab` is conditionally
rendered only when `activeTab === "protocol"`. So as soon as an operator
with a loaded session opens the Raw data (protocol) tab, both overlay
instances are simultaneously in the DOM, exactly as the FB doc's "정정 2"
anticipated.

## 2. Raw data (protocol) tab mount — full-plate scope

`ProtocolTab()` now renders `<AmplificationOverlay idPrefix="rawdata-" />`
(no `ploidyOverride`, so it reads `useSettingsStore.ploidy` — the whole-plate
setting) as a sibling **after** `<ProtocolEditor>`, not inside it.

Deliberately placed outside `ProtocolEditor`'s `<form onSubmit={handleSave}>`:
the overlay's toggle `<button>` had no explicit `type` attribute. A bare
`<button>` inside a `<form>` defaults to `type="submit"` — nesting the
overlay inside the protocol-save form as originally written would have made
clicking "Show Overlay" **submit the protocol form** (an unrelated
side-effect neither in the FB doc's list of known issues nor desirable).
Fixed both ways, belt-and-braces: the toggle button now has explicit
`type="button"` (in `AmplificationOverlay.tsx`, so the marker/Analysis-tab
instances are equally protected in case they're ever moved into a form),
*and* the Raw data mount sits outside the form entirely.

The Analysis tab's existing mount (`AnalysisTab.tsx`) is unchanged in
behavior — kept, not removed, with a comment recording why (mid-analysis
curve checks, and it's the only mount that can take
`MultiMarkerAnalysisPanel`'s `ploidyOverride` for marker-scoped curves).

## 3. Processing status — response echo, not the settings-store request

`AmplificationOverlay` now keeps the whole fetched `AmplificationResponse` in
state (previously it only kept curves derived data ad hoc inside the fetch
closure). A new `OverlayProcessingStatus` sub-component renders:

```tsx
<OverlayProcessingStatus
  requestedRox={useRox}
  normalizationApplied={response.normalization_applied ?? useRox}
  backgroundMode={response.background_mode ?? backgroundMode}
/>
```

`response.normalization_applied` / `response.background_mode` are the fields
`e5edefc` added to `/amplification/all`; they are what render, not
`useSettingsStore`'s `useRox`/`backgroundMode` request values. The `?? useRox`
/ `?? backgroundMode` fallback exists only for backward compatibility with a
hypothetical older backend response missing the fields (both are typed
optional in `types/api.ts` to mirror `ScatterResponse`/`PlateResponse`); the
live backend on this branch always sends them, so the fallback path is not
normally exercised.

Test (`AmplificationOverlay.rawdata.test.tsx`, "shows the response-echoed
processing status, not the requested settings value") mocks
`useRox: true` (settings-store) but `getAllAmplification` resolving with
`normalization_applied: false` — the honest "run has no usable passive
reference, stayed raw" case from the FB doc. Asserts
`data-requested="true"` / `data-applied="false"` on
`[data-testid="overlay-processing-status"]`, i.e. the badge reports what
actually happened, not what was asked for. Uses the existing
`t.chartBackground()` helper for the background-mode phrase (already used by
`SettingsTab`/QC copy) rather than inventing a new one.

## 4. Color-by selector: 유전형 / 웰 타입 / 단색

Added a `colorBy: "genotype" | "wellType" | "solid"` selector
(`#${idPrefix}overlay-color-by-select`). `유전형` (default, unchanged
behavior) uses `curve.effective_type`; `웰 타입` uses
`wellTypeAssignments[curve.well]` — both go through the same `wellInfo()`
helper `PlateView.tsx:144` already uses for exactly this genotype/well-type
duality, so no new color logic was invented. `단색` uses one fixed swatch
(`#2563eb` light / `#3b82f6` dark, matching `--color-primary`) for every
trace, with `showlegend: false` (a single flat color is not a "group" and
should not claim to be one via a fake legend entry).

**`단색` is not labeled or treated as "raw"**: the `Y` values plotted are
`curve.norm_fam` / `curve.norm_allele2` in every `colorBy` mode — normalization
and background correction already happened server-side before the curve
reaches this component. Both locale strings say "Solid color" / "단색" with
an inline code comment on each explicitly stating it is *not* a raw-signal
view (`en.ts`/`ko.ts`, next to `overlayColorBySolid`). No claim of "raw" is
made anywhere in the new copy.

Test ("color-by 'solid' strips genotype-driven trace colors without
re-fetching"): with two curves of different `effective_type`, genotype mode
produces 2 distinct trace colors; switching to `단색` produces 1. The same
test also asserts `getAllAmplificationMock` was called exactly once across
both renders — see §6.

The fetch effect and the render effect were split (previously one effect did
both, keyed on `[visible, channel, sessionId, useRox, backgroundMode, ...]`).
The fetch effect now depends only on `[visible, sessionId, useRox,
backgroundMode]` — the request-relevant settings — storing the whole
response in state. A second effect depends on
`[visible, response, channel, colorBy, ploidy, dark, wellTypeAssignments,
roleLabels, allele2Dye]` and only calls `Plotly.react` over the
already-fetched curves. This means switching `colorBy` **or** `channel`
(FAM/allele2 — the response already carries both) now re-renders instantly
without a network round trip, which was not true before for `channel` either
(pre-existing minor inefficiency, fixed as a side effect of this refactor,
not called out as a requirement but verified not to regress anything).

## Follow-up — the `?? useRox` fallback reasserted the request value

Review caught a residual bug in the code as first committed (`c4430fe`):

```tsx
normalizationApplied={response.normalization_applied ?? useRox}
backgroundMode={response.background_mode ?? backgroundMode}
```

`normalization_applied`/`background_mode` are typed *optional* on
`AmplificationResponse` (`types/api.ts:641`, kept optional deliberately for a
hypothetical older backend response shape predating `e5edefc`'s echo). So
this fallback path is real, and it reproduces exactly the bug this task
exists to remove: when the echo is absent, it silently asserts "applied" (or
"not applied") from `useRox` — the *request* — rather than admitting the
result is unknown. "Not reported" and "not applied" are different facts.

### RED verification

Added a new test ("does not assert 'applied' from the request when the
response omits the echo": `useRox: true`, response with
`normalization_applied` entirely absent). Ran it against the pre-fix
component (temporarily restored the `c4430fe` version of
`AmplificationOverlay.tsx` via `git show HEAD:...`, ran the test, confirmed
failure, then restored the fix):

```
FAIL  does not assert "applied" from the request when the response omits the echo
Expected the element to have attribute:
  data-applied="unreported"
Received:
  data-applied="true"
```

i.e. the old code asserted "applied: yes" purely from `useRox=true`, with no
echo at all backing that claim — confirmed RED before the fix.

### Fix

`OverlayProcessingStatus` now takes `normalizationApplied: boolean |
undefined` and `backgroundMode: BackgroundMode | undefined` directly from
the response (no `??` fallback to settings-store at the call site). A
`reported = normalizationApplied !== undefined` flag selects a third render
path:

- `reported && applied` → `t.overlayProcessingStatus(requestedRox, true)`,
  `data-applied="true"`
- `reported && !applied` → `t.overlayProcessingStatus(requestedRox, false)`,
  `data-applied="false"`
- `!reported` → new `t.overlayProcessingStatusUnreported(requestedRox)`,
  `data-applied="unreported"`

`backgroundMode` needed no equivalent new string: `t.chartBackground()`
(pre-existing, already used by `SettingsTab`/QC copy) already falls back to
its own "unknown"/"미확인" copy for any mode string it doesn't recognize,
so passing `backgroundMode ?? ""` reuses that existing honest fallback
rather than inventing a second one.

New locale keys `overlayProcessingStatusUnreported` added to both
`en.ts`/`ko.ts`, next to `overlayProcessingStatus`.
