## Key fact this task turns on (corrected by review, restated from the brief)

`navigation-store` does **not** persist. Position survives through exactly
two paths: the URL (`lib/workspace-history.ts` writes it,
`hooks/use-workspace-location.ts` wires the sync) and
`session-store.sessionQueries` (per-open-plate query strings in
`sessionStorage`, key `qprism-file-workspace`). So this task is legacy
**query-string parsing + canonical rewrite**, not a store migration. The
crash-safe fallback for an unrecognized tab id already existed
(`navigation-store.ts`'s `parseNavigation` → `tab()` type guard, unchanged by
this task) — but a fallback alone loses the user's actual destination
(`?tab=analysis&surface=plate` would drop to the default tab, not "Plate
Setup"). The new work is the **meaning-preserving mapping** that runs before
that fallback ever has to trigger.

## GREEN — implementation

### 1. `remapLegacyQuery` (`navigation-store.ts`)

A pure `(query: string) => string` function, placed in `navigation-store.ts`
per the task brief's explicit allowance ("매핑 함수가 여기 있어야 자연스러우면
허용") — it has zero store dependencies, so putting it here (rather than in
`workspace-location.ts`, which already imports `session-store.ts`, or in
`session-store.ts` itself) avoids a circular import between the two
consumers (`workspace-location.ts` and `session-store.ts`, which do not
import each other).

Mapping table (meaning-preserving, matches FB-07 §3-1's explicit table):

| Old query | New `tab` | New `surface` |
|---|---|---|
| `tab=analysis&surface=plate` | `plate` | `plate` |
| `tab=analysis&surface=analysis` | `results` | `analysis` |
| `tab=analysis` (no `surface`) | `plate` | `plate` |
| `tab=protocol` | `rawdata` | *(untouched — `rawdata` never reads `surface`)* |
| anything else (no legacy `tab`) | **unchanged, same string** | — |

The "no `surface`" row maps to `plate`, not `results`: the pre-P3-S1-T1
`initial.surface` was `'plate'` (confirmed via `git show e13c349^:...
navigation-store.ts`), i.e. `'plate'` was always the old default surface
when the query didn't specify one, so this reproduces that default exactly
rather than picking a new default.

`surface` is **set explicitly, never deleted**, for the `tab=analysis` case
(both when it's known and — importantly — when it's absent from the query).
This is because `AnalysisWorkspace.tsx` (untouched, outside this task's
scope) reads `state.surface` *directly* (`activeSurface`) to decide which of
its two DOM panels is visible — it does not go through
`resolveDisplayTab`. If the remap had merely dropped `surface` and let
`parseNavigation`'s domain default apply (`workspace-ready.ts` hardcodes
`surface: 'analysis'` as its saved-session default), a remapped `tab=plate`
URL would highlight "Plate Setup" in the top nav while
`AnalysisWorkspace` kept showing the Results panel underneath — a real
tab/content mismatch, not merely a cosmetic gap. Setting `surface`
consistently with the resolved `tab` closes that.

An already-canonical (or simply unrelated/unrecognized) query is returned
as the **exact same string reference value** — no `URLSearchParams`
round-trip, no reordering — so every existing test asserting
`location.search`/`restoreQuery` byte-for-byte (e.g.
`workspace-location.test.ts`'s original `?session=s&cycle=0` case) is
unaffected.

### 2. Canonical rewrite on page load (`workspace-location.ts`)

`createLocationRestore.run()` now computes `query =
remapLegacyQuery(location.search)` immediately after the owner check (same
position the original code read `location.search`), and calls
`history.replaceState(null, '', ...)` to rewrite the address bar to the
canonical form **before** the (async) session lookup even starts, so:
- a refresh always shows the new URL, regardless of whether the session
  lookup that follows succeeds or fails;
- the remapped `query` (not the raw one) flows into
  `useSessionStore.getState().setSession(session, info, 'reopen', query)`,
  so `restoreQuery` — and therefore the `NavigationValue` that
  `parseNavigation` eventually produces — is already canonical.

`query !== rawQuery` is the exact same reference-equality check
`remapLegacyQuery` is designed to make cheap: it's `false` (no rewrite) for
every URL that had nothing legacy in it.

### 3. `session-store.sessionQueries` (`session-store.ts`)

`loadSession(id)` now runs the remembered query for `id` through
`remapLegacyQuery` before handing it to `setSession(...)` as the restore
query — same mapping, applied at the one place a stored
`sessionQueries` entry is ever read back. Entries are written verbatim
from `location.search` at the moment a *different* session becomes active
(`setSession`'s "remember where the outgoing plate was" logic, untouched);
since `location.search` is canonical from this point forward (item 2 above
ensures a legacy URL never round-trips as legacy past its first load), only
**pre-existing** `sessionStorage` entries — already-open plates left over
from before this deploy — can still hold a legacy string, and this is
exactly where they get normalized back to a real tab id instead of losing
the operator's position.

### 4. `quality-navigation.ts` — stop producing the legacy value at its source

`apply()` used to write `useNavigationStore.setState({ tab: 'analysis',
surface, ... })` on every quality-target jump. `navigationTabs`/
`parseNavigation`'s `tab()` guard no longer recognize `'analysis'` as a tab
id post-P3-S1-T1 (that's the whole point of P3-S1-T1's restructure), so this
was a genuine, load-bearing bug: `workspace-history.ts`'s
`writeQualityChange` serializes this same state into the browser history
entry for the quality jump (`tab=analysis` in the URL), and popping that
entry back (`restoreQualityNavigation(null, query)` → `parseNavigation`)
would reject it with `reasons: ['tab']` and throw — silently breaking
back-navigation out of a quality target. Same for `returnFromQuality()`,
which serializes the same state.

Fix: derive the tab straight from `surface` — `tab: surface === 'plate' ?
'plate' : 'results'` — instead of the literal `'analysis'`. `surface` itself
is unchanged (still `'plate' | 'analysis'`, still consumed by
`quality-target.ts`/`AnalysisWorkspace.tsx`, both outside this task's
scope). This closes the AC "품질 탭 → 웰/마커 복귀 경로가 새 탭 구조에서
동작한다": both the *forward* jump (now writes a URL-parseable tab id) and
the *return* (`finishReturn`'s captured `view.tab`, read from `nav.tab`
*before* the jump, was already always a real tab id — unaffected, but now
provably round-trips through the URL too, see the new regression test).

`StoredTab`'s `'analysis'` member, `isWorkspaceTab`, and `resolveDisplayTab`
were **deliberately left in place** rather than deleted, even though the
P3-S1-T1 handoff note suggested they *could* now be removed once this one
remaining writer stopped: forbidden/adjacent-forbidden test files (root
`tests/**`, `App.analysis.test.tsx`, `CycleControl.test.tsx`,
`use-keyboard-assignment.test.ts`, `use-quality-focus.test.tsx`,
`workspace-history.test.ts`, etc. — see P3-S1-T1's own evidence for the
full list) still construct `tab: 'analysis'` directly as a generic
"workspace is open" placeholder, and none of those files are in this task's
write scope. Removing the type/helpers would be a type error in files this
task may not touch. This is a follow-up cleanup opportunity, not an AC of
this task.

### Why `App.tsx`/`lib/feedback-context.ts` needed no change

`App.tsx`'s `activeTab` is already computed as `resolveDisplayTab(state.tab,
state.surface)` (added by P3-S1-T1), and `<FeedbackWidget pageKey={activeTab}
/>` was already wired to that computed value, not to the raw store field.
Since `resolveDisplayTab` never returns `'analysis'` and this task's fix
means `quality-navigation.ts` no longer even writes it, `activeTab` — and
therefore every **newly submitted** feedback item's `page_key` — already
records `'plate'` / `'rawdata'` / `'results'` with no further code change.
Verified by reading `App.tsx:66,241` and confirming no other write site for
`FeedbackContext.page_key` exists (`lib/feedback-context.ts:38-39` only
copies whatever `pageKey` string it's given; it does no tab-id logic of its
own and needed no change either).

### Feedback `page_key` — old ↔ new mapping (for already-stored feedback)

This is a **display-time note for the admin panel**, not a data migration:
`describeFeedbackContext` (`lib/feedback-context.ts:63-79`) simply displays
whatever string is in a stored item's `page_key` — no code special-cases
old values, so already-stored items keep showing their original string
verbatim, while newly-submitted items show the new one. Per the orchestrator
handoff, 7 feedback items currently in the system carry the old values.

| Stored `page_key` (existing feedback, unchanged) | Equivalent new tab (for newly-submitted feedback) |
|---|---|
| `analysis` (submitted from the Plate Setup sub-surface) | `plate` |
| `analysis` (submitted from the Analysis sub-surface) | `results` |
| `protocol` | `rawdata` |

No reconciliation of already-stored `page_key` values was performed or
requested by the AC (which asks only that the mapping be *recorded*, and
that new submissions use the new ids — both satisfied).
