## Problem

FB-03 §8 wants low-signal "analysis warnings" demotable to the bottom of the
results screen, but the backend's `warnings` field (`ClusteringResult` /
`RegionResult`, `app/models.py:340`/`:433` before this change) is an
unqualified `list[str]` of diagnostic codes with no severity distinction.
Demoting a code that bears on genotype-call reliability (not just cosmetics)
without a severity contract first would hide something the operator needs to
see.

The backend currently produces exactly three codes, all from
`app/processing/clustering.py`:

| code | emitted at | what it means |
| --- | --- | --- |
| `relative_ntc` | `clustering.py:360` | The auto-NTC gap test was inconclusive; affected wells are relabelled Undetermined instead of NTC. Changes the reported call outcome for those wells. |
| `low_n` | `clustering.py:385` | Fewer than 4 signal wells — no mixture model was fit; calls are capped at `_SMALL_REGION_CONFIDENCE` because there is no statistical evidence behind them ("C3"). |
| `anchor_conflict` | `clustering.py:838` | The operator's allele-1/allele-2 anchor wells are mutually inconsistent (inverted/degenerate scale); the anchor-based dosage-origin scale is discarded and the unanchored fallback is used instead. |

## GREEN — implementation

### Contract shape (`app/models.py`)

- `WarningSeverity = Literal["blocking", "advisory"]`.
- `WARNING_SEVERITY: dict[str, WarningSeverity]` — the per-code classification
  table, with the rationale above written as an in-code comment next to it
  (see `app/models.py` immediately above `class RegionResult`).
- `_DEFAULT_WARNING_SEVERITY: WarningSeverity = "blocking"` — the default for
  a code not in the table.
- `class WarningDetail(BaseModel): code: str; severity: WarningSeverity`.
- `_graded_warnings(codes: list[str] | None) -> list[WarningDetail] | None` —
  maps a code list through `WARNING_SEVERITY`, returning `None` (not `[]`)
  when `codes` is falsy, mirroring the existing `warnings` contract.
- `RegionResult.warning_details` and `ClusteringResult.warning_details` are
  **new `@computed_field` properties** derived from the existing `warnings`
  field via `_graded_warnings(self.warnings)`. No changes were needed in
  `app/processing/clustering.py` or `app/routers/clustering.py` — severity is
  derived at read time from the codes those modules already append to
  `warnings`, so the single source of truth for "what warnings exist" stays
  where it was.

### Severity classification decided

All three known codes are classified `blocking`:

```python
WARNING_SEVERITY: dict[str, WarningSeverity] = {
    "relative_ntc": "blocking",
    "low_n": "blocking",
    "anchor_conflict": "blocking",
}
```

Rationale (also written in-line in `app/models.py` and
`frontend/src/lib/analysis-warnings.ts`):

- **`relative_ntc`** changes the reported call outcome for the flagged wells
  (NTC → Undetermined). The warning text itself says assigning a real NTC
  well would fix the ratio origin — the ratio origin is what every genotype
  call in the marker is measured against.
- **`low_n`** marks calls made with **no statistical evidence** (no mixture
  fit; confidence explicitly capped) — precisely the case a human reviewer
  needs visibility into.
- **`anchor_conflict`** means the operator-declared dosage-origin anchors
  were discarded as mutually inconsistent; the anchors define where dosage 0
  and dosage `ploidy` sit on the measured axis, i.e. the origin every
  genotype call in the marker is measured against.

**No warning is demoted by this task.** The severity table is the mechanism
for a *future* purely-informational warning to be demoted (FB-03 §3-1); this
task classifies only the three codes that exist today, all conservatively as
`blocking`. Reclassifying any of the three to `advisory` is a QC policy
decision for the product owner, not something inferred here.

An unrecognised/future code defaults to `blocking` (showing an unfamiliar
diagnostic prominently is safer than silently demoting one nobody has
vetted).

### Frontend mirror (`frontend/src/lib/analysis-warnings.ts`, `frontend/src/types/api.ts`)

- `types/api.ts`: added `WarningSeverity` / `WarningDetail` types and an
  optional `warning_details?: WarningDetail[] | null` field on both
  `ClusteringResult` and `RegionResult`, alongside the untouched `warnings`
  field.
- `analysis-warnings.ts`: added `analysisWarningSeverity(code)` (same
  table/default/rationale as the backend, kept in a comment) and
  `gradedAnalysisWarnings(codes, t)`, a convenience combinator returning
  `{ code, text, severity }[]` for a future consumer that needs to split
  warnings by severity. **No existing export was changed**; `AnalysisTab.tsx`
  (which calls `analysisWarningTexts(codes, t)`) was not touched — that
  wiring is P4-S3-T1's scope, not this task's.

## Backward compatibility

- The existing `warnings: list[str] | None` field on both models is
  byte-for-byte unchanged — same name, same type, same `None`-when-clean
  semantics.
- `warning_details` is strictly additive (a new computed field / new
  optional TS field). A consumer that reads only `warnings` and has never
  heard of `warning_details` continues to work identically — asserted
  directly in
  `test_legacy_consumer_reading_only_warnings_list_is_unaffected` (backend)
  and by leaving `AnalysisTab.tsx` / the other three FE files unmodified
  (frontend).
- Existing dict-shaped tests that assert specific keys on clustering/region
  JSON (`tests/test_marker_contract.py`, `app/routers/statistics.py`,
  `app/routers/qc.py`) check `by_id["m1"]["warnings"]` etc., not full-dict
  equality, so the new additive key does not break them (confirmed by the
  full backend run below).
