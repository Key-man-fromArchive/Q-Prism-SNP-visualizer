## Problem (FB-04 §3-1, feedback `7ec0ec1e5e8a4870`)

`.analysis-scatter-canvas` was declared twice inside the same `@media
(min-width: 1280px)` block in `index.css`:

```
:179  .analysis-scatter-canvas { max-height: 300px; }
:188  .analysis-scatter-canvas { height: 360px; }
```

Different properties, so the cascade does not let the second rule replace
the first -- both apply, and `max-height: 300px` wins the used value on any
viewport ≥1280px. Wider screens got a *smaller* canvas. Fixing only that
duplication is not sufficient: at 1920×911 (2-column grid, ~940px column)
a literal `aspect-ratio: 4/3; max-height: 70vh` still clips to 638px
(`70vh` of 911) against the 705px a 4:3 ratio needs at that width, landing
on ~1.47:1 -- neither 4:3 nor square. Height-based clamping cannot hold an
aspect ratio; the box has to be bound by width instead.

## GREEN — implementation

### `index.css`

Removed both conflicting 1280px-block declarations (`:179`, `:188` in the
pre-change file) and replaced the single base rule with a width-bound
`aspect-ratio`:

```css
.analysis-scatter-canvas {
  --scatter-max-h: min(70vh, 640px);
  --scatter-aspect-w: 4;
  --scatter-aspect-h: 3;
  aspect-ratio: var(--scatter-aspect-w) / var(--scatter-aspect-h);
  height: auto;
  width: 100%;
  max-width: calc(var(--scatter-max-h) * var(--scatter-aspect-w) / var(--scatter-aspect-h));
  min-height: 360px;
  margin-inline: auto;
}
```

No media-query-specific override remains for this class -- `min(70vh,
640px)` already bounds the canvas identically at 1920, 1280, 768 and 400px,
which is what let the duplicate 1280px rule be deleted outright instead of
merged into one 1280px rule (the original bug's root cause, gone rather
than patched over). The `4`/`3` literals in the base rule are only the
pre-hydration fallback; the live values come from the inline
`--scatter-aspect-w/h` the two components set from `settings-store
.scatterAspect` (below), so a real page paints with the *store's* value
before this fallback would ever be visible.

**Width-bound math (matches FB-04 §3-1's target table for a ~904px column
at 1920×911):**
- `4:3`: `max-width = min(70vh, 640px) * 4/3`. `70vh` of 911px ≈ 637.7px
  (< 640px cap) → `max-width ≈ 850px`, height ≈ 638px (4:3 held exactly by
  construction). Doc's target was 853×640 -- the ~3px difference is the
  doc's own viewport-chrome rounding, not a defect in this formula.
- `1:1`: `max-width = min(70vh, 640px) * 1/1 ≈ 638px`, height ≈ 638px.
  Doc's target: 640×640.
- At any width narrower than the ratio's `max-width` (e.g. a 400px
  single-column layout), the box's actual width shrinks below `max-width`
  and `aspect-ratio` keeps height in lockstep -- height never exceeds the
  `--scatter-max-h` bound at any breakpoint, satisfying "1280/768/400px에서
  뷰포트 세로를 넘지 않는다" without any per-breakpoint override.
- `min-height: 360px` can win over the ratio-derived height only at very
  narrow widths where `width * 3/4 < 360px` (below ~480px for 4:3). That is
  intentional per FB-04 §3-1 ("좁은 폭에서는 min-height가 이겨 세로가 더
  길어진다 — 의도된 동작") and matches the user's own direction ("세로가
  낮다"), not a bug.

### `settings-store.ts`

Added `scatterAspect: '4:3' | '1:1'` (default `'4:3'`) and
`setScatterAspect`, following the exact pattern of the adjacent
`scatterTool`/`setScatterTool` field: included in `defaults`, included in
`resetToDefaults` (via the `defaults` spread), a plain `set({
scatterAspect: v })` setter. No change to the `persist` config (`name:
'snp-analyzer-settings'`) -- zustand's default `merge` is `{ ...currentState,
...persistedState }`, so a pre-existing localStorage payload that has no
`scatterAspect` key contributes nothing for that key and the `defaults`
value baked into `currentState` at construction survives untouched. This
was verified directly (see Preset/persist compatibility below) rather than
assumed.

### `ScatterPlot.tsx` / `MarkerScatterPlot.tsx`

Both:
- read `scatterAspect` via `useSettingsStore((s) => s.scatterAspect)`.
- a small `scatterAspectVars(aspect)` module-level helper (duplicated
  verbatim in both files, each commented as pointing at the other --
  no shared file exists in this task's write scope to hold one copy)
  maps `'1:1'` → `{w:1,h:1}` / `'4:3'` → `{w:4,h:3}` and returns them as
  the `--scatter-aspect-w`/`--scatter-aspect-h` inline style properties.
- that style is applied to the element carrying `.analysis-scatter-canvas`
  in each file: the outer wrapper `<div>` in `ScatterPlot.tsx` (the actual
  Plotly mount `#scatter-plot` is a `width:100%; height:100%` child of it,
  so it inherits the ratio-derived box size), and directly on the Plotly
  mount `<div data-testid="marker-scatter">` in `MarkerScatterPlot.tsx`
  (that file has no separate wrapper).
- a new, narrowly-scoped `useEffect(() => { ... }, [scatterAspect])` calls
  `Plotly.Plots.resize(el)` (via an optional-chained lookup, so it is a
  no-op against any existing test's Plotly mock that does not stub
  `Plots`) once `initialized.current` is true. `config.responsive: true`
  was already present on both plots' Plotly config and unchanged by this
  task -- in a real browser, Plotly's own internal `ResizeObserver`
  (attached because of that flag) already reacts to the CSS-driven size
  change with no code of ours needed. This explicit call exists so the
  redraw is deterministic and, more importantly, *testable*: jsdom has no
  layout engine, so nothing in a unit test ever fires a real
  `ResizeObserver` callback, and this task's own AC ("종횡비 전환 후
  Plotly가 다시 그려진다") would otherwise be unverifiable here. The main
  render effect (the one building `traces`/`layout` and calling
  `Plotly.newPlot`/`.react`) was deliberately **not** given `scatterAspect`
  as a dependency -- toggling the ratio changes no trace or axis data, only
  the container's pixel size, so re-running the full render effect for it
  would be wasted work; the size-only resize effect is the correct,
  narrower fix.

### `lockAspect` interaction (checked, not changed)

`lockAspect`/`scaleanchor:'x'`/`scaleratio:1` in `axisRangeLayout()`
(`lib/scatter-axes.ts`, unmodified, out of write scope) fix the
*data*-space ratio (RFU-per-pixel equal on both axes); the canvas
`aspect-ratio` fixes the *container* box. Plotly's own `constrain:
'domain'` behavior for a `scaleratio`-locked axis pair already only ever
shrinks the plotting **area** inside whatever box it is given -- it does
not, and did not before this task, resize the container itself -- so the
two settings compose (locked data-ratio inside a resized container)
without any new interaction to guard. No `scatter-axes.ts` change was
needed or made.

omits `scatterAspect`) for the same conclusion at the persistence-merge
level, since round-tripping an actual pre-P4-S1-T1 localStorage payload
through the `persist` middleware's storage adapter isn't exercisable from
a unit test (that middleware only reads storage once, at module
construction). Neither `apply-preset.ts` nor `use-preset-operations.ts`
needed a change; per the assignment, this is reported rather than edited.

## jsdom limitations (explicit, per assignment)

jsdom implements neither CSS `aspect-ratio` layout nor `ResizeObserver`, so
none of the following AC items are verifiable as *measured pixel output*
from this task's unit tests, and are left for the VIEWPORT/E2E/ROOT-E2E
gates the task table already assigns:
- "캔버스 `boundingBox()`의 width:height가 4:3 ±2%" and the 1:1 equivalent
  — the width-bound math above is the analytic argument; a real
  `boundingBox()` measurement needs a real browser.
- "1280/768/400px에서 뷰포트 세로를 넘지 않는다" — same, needs real layout.
- "마운트 직후 캔버스 높이가 0이 아니다" — `min-height: 360px` guarantees
  this in a real browser; jsdom elements report `clientHeight: 0`
  regardless of any CSS, so this can't be asserted here either way.

What **is** verified here, and is the part actually owned by this task's
write scope:
- the correct `--scatter-aspect-w`/`-h` values are set on the canvas
  element for both plots, by default and after `setScatterAspect('1:1')`
  (`ScatterPlot.aspect.test.tsx`, `MarkerScatterPlot.aspect.test.tsx`).
- `Plotly.Plots.resize` fires exactly once, after the initial mount,
  when-and-only-when `scatterAspect` actually changes (not on an
  unrelated re-render, and not before `Plotly.newPlot` has resolved) --
  for both plots.
- the store's default/reset/legacy-preset-compatibility behavior
  (`settings-store.test.ts`).

## PNG export gap found (reported, not fixed — out of write scope)

`src/hooks/use-exports.ts`'s `exportPNG` calls `Plotly.toImage(chart.element,
{ format: 'png', width: 1200, height: 900, scale: 2 })` — a **fixed** 4:3
(1200×900) capture size regardless of the on-screen canvas's actual
measured size or the selected `scatterAspect`. With `scatterAspect: '1:1'`
the exported PNG will still be a 1200×900 (4:3) image, not a square one
matching the screen. This was the specific "미검증" item FB-04 §6 flagged
("`hooks/use-exports.ts`의 캡처가 실측 크기를 쓰는지 고정값을 쓰는지 —
착수 시 확인 필요") and this task's own AC list repeats it. `hooks/` is
outside this task's write scope (owned elsewhere per the Write Scope list),
so it was inspected but not modified. This is a real, pre-existing gap
against the AC "PNG/PDF 내보내기 산출물이 두 종횡비 모두에서 정상이다" and
should be tracked as follow-up work (a candidate for whichever task next
touches `use-exports.ts`, e.g. P4-S2-T1 or a dedicated fix), not silently
left unmentioned. PDF export (`exportPdf()`) is a backend-rendered
document fetched over the network, unrelated to this frontend canvas size.
