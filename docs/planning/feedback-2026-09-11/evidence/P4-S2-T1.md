## Problem (FB-04 §3-2/§3-3, feedback `7ec0ec1e5e8a4870`, item 3 and 4)

The normalization checkbox (`scatter-use-rox`) and the axis min/max inputs
(`axis-x-min`/`max`, `axis-y-min`/`max`) already existed, but only inside a
collapsed `<details data-testid="analysis-advanced-settings">` alongside four
other control groups (drag tool, NTC axis offsets, NTC quadrant, dosage
ceiling) — a discoverability defect, not a missing feature. The user read
this as "I have to go into the Settings tab to normalize" because
`SettingsTab.tsx` carried a second, more visible copy of the same `useRox`
toggle. The axis inputs were also gated by `numberInput(..., !manual)`, so
`axisMode` had to be switched to "Manual" in the dropdown *before* an
operator could type a bound — item 4 of the feedback asks for the reverse:
clicking "축 설정" should let the operator type first.

## GREEN — implementation

`ScatterViewControls.tsx` now renders two siblings instead of one collapsed
panel:

1. **`data-testid="scatter-plot-header"`** (new, always visible, first) —
   drag-tool toggle, normalization checkbox + reference-channel dropdown +
   outlier warning, axis-mode select + "fit to data" + lock-aspect + a new
   **"축 설정…" (`axis-settings-toggle`)** button that opens an inline
   popover (`axis-settings-popover`) holding the four `axis-x-min/max`,
   `axis-y-min/max` inputs, and the new **`scatter-aspect-select`** dropdown
   bound to P4-S1-T1's `settings-store.scatterAspect` /
   `setScatterAspect`.
2. **`data-testid="analysis-advanced-settings"`** (unchanged position/id,
   still closed by default) — now holds only NTC axis offsets, the NTC
   quadrant and the dosage ceiling: the three low-frequency, expert
   settings. Its `<summary>` text (thresholds, axis-mode label,
   `ScatterReferenceBasis`, aspect state) was left **byte-for-byte
   unchanged** — the six pre-existing tests assert on that exact text, and
   the task's own instruction was position-only movement, not a rewrite.

`axis-settings-toggle` forces `axisMode` to `'manual'` on open
(`toggleAxisSettings`: `if (!manual) setAxisMode('manual')`); the popover is
gated on `manual && axisPopoverOpen`, so switching the axis-mode dropdown
away from Manual closes it automatically instead of leaving disabled inputs
open. This satisfies feedback item 4 literally — clicking the button is now
the way to get to manual bounds, not a prerequisite for it.

The reference-channel dropdown intentionally carries **one option** —
`normalizationLabel(labels)`, the channel actually in force — per FB-04 §3-4
Step 1: the saved session model keeps a single reference slot
(`app/models.py` fam/allele2/reference), so runtime re-assignment to an
arbitrary collected channel is out of scope (would need a storage-model
change, listed there as a separate, backend-scoped follow-up). Both the
checkbox and the select are `disabled` when `hasNormalizationChannel` is
false, with a `normalization-channel-reason` span explaining why. This prop
already existed on `ScatterViewControlsProps` but neither `ScatterPlot.tsx`
nor `MarkerScatterPlot.tsx` ever passed it (it silently defaulted to `true`
in both plots regardless of the actual run). Both now wire
`hasNormalizationChannel={useSessionStore((s) => s.sessionInfo?.has_rox ===
true)}` — the same `has_rox` flag `SettingsTab.tsx` already used to decide
whether to render its own normalization card, so the two plots and the
settings tab now agree on when a run has no reference channel.

### `SettingsTab.tsx` de-duplication

The `rox-normalize-checkbox` (editable, `onChange={setUseRox}`) is removed.
`settings-store.useRox` is **not** removed — it is still read here (for
display) and still written from the plot header and from preset application
(`setUseRox` stays in the memoized preset-apply callback). The card now
shows `t.roxNormalization`, the existing `t.roxDescription`, and a new
read-only line, `data-testid="rox-normalize-status"`:

> "Currently on/off. Adjust it from the checkbox above the
> allele-discrimination plot, not here." (`roxNormalizationMovedNotice`)

Two new tests cover this: the panel reports state without exposing a second
editable checkbox (`queryByRole('checkbox', { name: /rox/i })` is null,
`rox-normalize-status` reflects `useRox` toggling), and the whole card still
does not render at all when `sessionInfo.has_rox` is false (unchanged
behavior). No existing `SettingsTab.test.tsx` case renders with
`sessionInfo.has_rox === true`, so none of the four pre-existing tests
touch this panel; they were unaffected before and after.

Verified structurally, not just by test pass/fail: `promotes drag tool,
normalization, axis mode and aspect above the collapsed advanced settings`
asserts each promoted id (`scatter-tool-select`, `scatter-tool-edit`,
`scatter-use-rox`, `axis-mode`, `axis-fit-to-data`, `axis-lock-aspect`,
`axis-settings-toggle`, `scatter-aspect-select`) both (a) exists in the

same test confirms `ntc-fam-max`, `ntc-axis-x-offset` and the
`scatter-view-controls` wrapper div are still inside the `<details>`,
exactly where they were. All ids named in the assignment
(`scatter-use-rox`, `axis-mode`, `axis-x-min/max`, `axis-y-min/max`,
`scatter-tool-select/edit`, `ntc-fam-max`, `ntc-allele2-max`,
`axis-lock-aspect`) are present, unchanged, in either location.

Note on `data-testid="scatter-view-controls"`: this id stayed on the *same*
inner div it always occupied, now inside `<details>` holding only the
demoted controls. The new always-visible header got a **new**, separate id
(`scatter-plot-header`) rather than reusing `scatter-view-controls`, to
avoid a duplicate-testid collision (two elements answering to one id is
itself a regression risk for any `getByTestId` caller, including the root
E2E suite's `tests/24-responsive.spec.ts`, which queries
`scatter-view-controls` after opening the `<details>` summary — that
assertion still passes because the div is still there and still visible,
just smaller).
