### Root cause

`scatter-plot-header`'s 4 control groups (drag tool, normalization, axis
range, aspect ratio) each stacked a visible text label over their control
row (`flex-col`), and the axis-range group alone spelled out full button
text ("Fit to data", "Equal x/y scale", "Axis settings…"). At the
`analysis-grid`'s ~902px column width, that combined width didn't fit one
row, wrapping the aspect-ratio group to a second row — 118px of header for
what is fundamentally one row's worth of controls. `--scatter-max-h: min(70vh, 640px)`
had no way to account for any of this: it's a fixed viewport-fraction/pixel
cap with no notion of how much chrome sits above it.

## Orchestrator correction — the height clamp reverted

The `calc(100dvh - 555px)` term added above was reverted. **The
"1920x911, no scroll" target it was built to satisfy was never in the
user's request** — it was written into the follow-up task, not the
feedback. The user (`7ec0ec1e5e8a4870`) asked for the scatter plot to be
"square, or at minimum a 4:3 portrait rectangle" because it read as "too
small, specifically too short vertically." FB-03 separately establishes
that scrolling for secondary content is acceptable ("분석경고 같은건 최하단에
있어도 충분합니다"). Nothing in either document asks for the canvas itself to
fit inside the initial viewport without scrolling.

Clamping `--scatter-max-h` to available height did technically stop the
canvas from running off-screen, but it did so by colliding with
`min-height: 360px` and sinking the rendered height to that floor — 360px
is only 60px above the 300px the user was already complaining about, and
the floor/cap collision also degraded the aspect ratio to an approximate
1.318/0.989 instead of exact 4:3/1:1. Chasing a no-scroll constraint that
was never requested ended up re-breaking the actual request (a visibly
taller, correctly-proportioned plot). This was this task's own error in an
earlier turn of this same followup, not a pre-existing defect.

**Reverted**: `--scatter-max-h` back to `min(70vh, 640px)` (`index.css`).
`min-height: 360px` is kept unchanged (Plotly 0-height guard) but no longer
collides with the cap in ordinary use, since nothing subtracts chrome from
it anymore.

  `role="group"` labels; icon-only fit-to-data/lock-aspect/axis-settings).
  This freed real vertical space above the canvas and stays.
- `ScatterReferenceBasis` / `normalization-state` left byte-for-byte

### What the two bars actually were
