Branch: `feedback/p5-upload` (worktree `worktree/feedback-p5`)

## Problem (FB-02, feedback `0de8fb3361884951`)

"멀티 업로드는 우측 상단이 아니라. 파일 입력시엔 업로드창 인근에 나와야합니다."
The FB-02 write-up's review corrections (read before starting, per the
assignment) established the real shape of the problem:

1. The central `UploadZone` drop zone **already** supports multi-file upload
   (`multiple` input + `runUploadJobs(files)`); the actual defect is two
   independent upload implementations with mismatched limits, and the
   `FileWorkspaceDrawer` trigger button living only in the header,
   off-screen from the upload flow the user is actually looking at.
2. The drawer's queue (`useState<QueueItem[]>`) is **not** persisted —
   `session-store`'s persist only covers `openSessionIds`/`sessionQueries`.
   Conditionally mounting/unmounting the drawer by session presence would
   destroy an in-flight upload queue the instant the upload it was tracking
   succeeds (since a new session flips `visibility.upload` to `false`). This
   was the binding constraint on the whole redesign.

## GREEN — implementation

**Store (`file-workspace-store.ts`, new, zustand, not persisted — matching
the queue's own non-persisted lifetime):** `open: boolean`, a
`triggers: Partial<Record<'header'|'inline', HTMLButtonElement>>` registry,
`setOpen`, `registerTrigger`, and `focusVisibleTrigger` (focuses whichever
trigger is currently registered, preferring `header` if both are somehow
present — they never are in practice, since exactly one placement is ever
mounted by `visibility.upload`).

**`FileWorkspaceTrigger.tsx` (new):** the only thing that used to live
inside the drawer's trigger `<button>`. Takes a `placement: 'header' |
'inline'` prop, reads/writes the shared store, shows the open-session count
badge (still read straight from `session-store`, not duplicated into the
new store), and registers/unregisters itself in the trigger registry on
mount/unmount. Keeps the same DOM `id="file-workspace-button"` the
`tests/18-file-workspace.spec.ts` E2E spec already selects by (safe, since
only one placement is ever mounted at a time), plus a
`data-testid="file-workspace-trigger-{placement}"` for placement-aware
assertions.

**`FileWorkspaceDrawer.tsx` (panel):** lost its trigger `<button>` and local
`triggerRef`/`open` state entirely; now reads `open`/`setOpen` from the
shared store and calls `focusVisibleTrigger()` on close (Escape, the X
button, the overlay, and after opening a session) instead of a captured
`triggerRef`. Returns `null` when closed and `createPortal(..., document.
body)` when open, so it is mounted **unconditionally** wherever the parent
puts it (App.tsx, once, permanently) without depending on being near either
trigger's DOM position. Its queue/session-list state (`useState`) is
completely unchanged — it survives visibility flips simply because the
component itself is never unmounted anymore.

**`App.tsx`:** mounts `<FileWorkspaceDrawer onOpenSession={() =>
setActiveTab('results')} onGoToProject={() => setActiveTab('project')} />`
unconditionally at the top level (same two callbacks Header used to own),
and passes `<Header showFileWorkspaceTrigger={!visibility.upload} />`.

**`Header.tsx`:** replaced the `<FileWorkspaceDrawer .../>` mount with
`{showFileWorkspaceTrigger && <FileWorkspaceTrigger placement="header" />}`.
`showFileWorkspaceTrigger` defaults to `true` so every existing render site
that doesn't pass it (all of `Header.test.tsx` except the three new cases)
keeps its current header unchanged.

**`UploadZone.tsx`:** added `<FileWorkspaceTrigger placement="inline" />` in
a centered row directly below the drop area/hidden inputs, above
`RecentSessions` — "인근", not a separate hero block (P6-S3-T1 brand work is
out of scope and untouched). Its label uses a new `workspaceManageFiles`
string ("Manage multiple files" / "여러 파일 관리하기") rather than the
header's compact "Files", since it needs to explain itself without the
header's surrounding session-management context.

**Limit/message parity (P5-S2-T1, D-7: roles stay separate, only numbers
and copy converge):** `lib/upload-jobs.ts` now exports `MAX_FILES_PER_DROP`
(20), `MAX_TOTAL_BYTES` (500 MB), `MAX_TOTAL_MB`, and
`uploadLimitViolation(files)`. `FileWorkspaceDrawer.enqueueFiles` was
changed to call this instead of its own inline count/byte checks (same
constants, same `t.workspaceTooManyFiles`/`t.workspaceTotalTooLarge`
messages, unchanged UI/queue implementation). `UploadZone.handleMultipleFiles`
previously had **no** limit check at all; it now filters to its own
supported-extension subset (mirroring the drawer's "supported first, then
limit" order) and applies the identical `uploadLimitViolation` check, using
the identical message strings, before doing anything else. Neither queue
implementation nor either mapping-wizard path was touched.

### New/changed test files

- `stores/file-workspace-store.test.ts` (new, 5 tests) — open/close,
  register/focus/unregister the trigger registry, header-over-inline
  preference.
- `components/upload/FileWorkspaceTrigger.test.tsx` (new, 10 tests) —
  placement-parameterized open/aria-expanded/badge/register-unregister,
  plus the distinct test-id and inline label.
- `components/upload/FileWorkspaceEntry.test.tsx` (new, 6 tests) — the
  acceptance-critical scenarios, using a small harness (`TestHost`/
  `ToggleableHost`) that mirrors App.tsx's actual wiring (one trigger
  visible at a time + the always-mounted panel) without pulling in all of
  App's auth/navigation machinery:
  - only the inline trigger shows with no session; only the header trigger
    (with badge) shows with one
  - the same queue reappears whether opened from the inline or the header
    trigger
  - **the queue and open state survive a session appearing mid-upload**
    (the core regression this task exists to prevent) — the inline trigger
    is dropped, the header trigger appears, the dialog and its queued item
    stay, and the upload finishes to `success` afterward
  - focus returns to the visible trigger on Escape (simple case)
  - focus returns to the **header** trigger (never the vanished inline
    one) after a close that follows a mid-upload session swap
- `components/upload/FileWorkspaceDrawer.test.tsx` — its 4 existing tests
  updated to open the panel through a rendered `FileWorkspaceTrigger`
  (`renderWorkspace()` helper) instead of a button the panel no longer
  renders itself; no assertions weakened.
- `components/upload/UploadZone.entry.test.tsx` — added: inline trigger
  renders and opens the shared store; a 2-file batch upload through
  `#file-input` still calls `uploadFile` twice and opens both sessions
  (regression guard for `multiple` + `runUploadJobs`); a 21-file drop and
  an oversized-total drop each produce the **exact same message string**
  (`en.workspaceTooManyFiles`/`en.workspaceTotalTooLarge`) the drawer uses.
- `lib/upload-jobs.test.ts` — added 3 `uploadLimitViolation` cases.
- `components/layout/Header.test.tsx` — added: default (`true`) shows the
  header trigger; explicit `false` hides it.
