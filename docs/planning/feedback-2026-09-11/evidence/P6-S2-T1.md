# P6-S2-T1 — Brand palette application (Deep Teal)

Branch: `feedback/p6-brand` (worktree `worktree/feedback-p6`), shared with
concurrent P6-S1-T1 work (product name unification, committed at `a32668c`
before this task started; no file overlap — see Write Scope below).

## Problem

`--color-primary` was Tailwind's default blue (`#2563eb`), not a brand
color, and it was byte-identical to `--color-fam` (the FAM/allele-1 channel
color). Buttons and FAM data points were visually indistinguishable, and
the palette read as generic/framework-default rather than branded — the
direct cause of the user feedback "사이트 페이지 전체의 UI가 너무 촌스럽습니다."

### Added: `--color-on-primary`

Not in the confirmed table but required by it: dark mode's new primary
(`#2dd4bf`, a light mint) fails WCAG AA with white text (~1.7:1 measured;
team-lead's brief flagged this explicitly). Added a new token, foreground
for anything sitting on a `--color-primary` surface:

- light: `#ffffff` (light-mode primary `#0f766e` keeps working with white,
  contrast 5.47 per the team-lead's brief)
- dark: `#0e1413` (same as `--color-bg` dark — a deliberate reuse, not a new
  arbitrary color; contrast against `#2dd4bf` is ~10:1)

Tailwind v4 auto-generates `bg-on-primary`/`text-on-primary`/etc. utilities
from any `--color-*` custom property in `@theme`, the same mechanism that
already produces `bg-primary`/`text-primary` — no Tailwind config change
needed.

### `--color-info`

Not in the confirmed table (team-lead's brief called this optional:
"검토해도 좋다"). It was `#2563eb`/`#60a5fa` — identical to `--color-fam` — the
same collision problem the whole task exists to fix, just for a second
consumer (`QualityTab.tsx`'s QC-range legend swatch, the only place that
reads it). Moved to `#0f766e`/`#2dd4bf` (same as `--color-primary`) so it no
longer aliases the FAM channel. `--color-danger`/`--color-warning`/
`--color-success` are untouched in both modes (locked by
`index.css.test.ts`).

## Hardcoded colors found and fixed

### 1. Cycle slider stayed blue regardless of palette (the reported symptom)

`CycleControl.tsx`'s `<input type="range">` had no color styling at all —
it was rendering the **browser's native accent color**, not anything from
this codebase. Fixed in `index.css`:

```css
input[type="range"] {
  accent-color: var(--color-primary);
}
```

Confirmed live in `p6-s2-t1-light-analysis.png` below (visible teal slider
fill/thumb).

### 2. `bg-primary` + hardcoded `text-white`: a dark-mode regression this task would otherwise introduce

Auditing every `--color-primary` consumer (not just the write-scope files)
surfaced that dozens of buttons pair Tailwind's `bg-primary` with a literal
`text-white`, including the shared `buttonVariants` primary variant
(`src/components/shared/ui/variants.ts`) and `ProtocolTab.tsx`'s own
"Add step" button (inline style, hardcoded `#3b82f6`/`white`, not even
using the token). With dark mode's primary now a light mint, white text on
it drops to ~1.7:1 contrast — invisible-looking buttons across nearly the
entire app. This is a regression *this palette change* would cause, not a
pre-existing bug, so it's in scope ("그 밖에 하드코딩 색을 토큰으로 바꾸는 데 꼭 필요한
컴포넌트").

Fixed by routing every `bg-primary`-paired `text-white` to the new
`text-on-primary` token (mechanical, same string swap everywhere):
